# AutoML Agent — LangGraph 기반 자율 실험 루프

원본 데이터에서 **데이터셋 카드(집계 요약)를 만들고**, 그 카드만 보고 **계획 →
모델 선택 → 학습 → 평가**를 수행하고, 목표 지표에 미달하면 **실패를 진단해 다시
계획**하는 순환 그래프입니다. 목표를 달성하거나 반복 예산이 끝나면 최종 보고서를
씁니다.

LLM은 원본 데이터를 한 행도 보지 않습니다. 그것을 규약이 아니라 **그래프 구조로**
보장합니다 — 아래 [원본 데이터 경계](#원본-데이터-경계)를 보세요.

```
      raw data (CSV)
            │
            ▼
      [profiling] ──────────────► data_ref  (비공개: 경로 + target 컬럼)
       subprocess                     │        실행 노드만 읽음
            │                         │
            ├──► goal  (목표 임계값 — auto 모드는 기준선에서 도출)
            │                         │
            └──► dataset_card         │       ← 데이터에서 추론으로 넘어가는
                    │ (집계만)         │         유일한 통로, 그리고 그것은
                    ▼                 ▼         노드 경계다
            [planning] ──► [model_selection] ──► [training] ──► [evaluate]
                 ▲             LLM                subprocess         │
                 │                                                   │
                 │                                            route()│  ← 종료 판단은 코드만
                 │                                                   │
              [critic] ◄──────────── critic ──────────────────────────┤
                LLM                                                   │ report
                                                                      ▼
                                                                 [holdout]  ← 반복이 한 번도
                                                                subprocess     보지 않은 test
                                                                      │        20%를 1회 채점
                                                                      ▼
                                                                  [report] ──► END
```

## 설계 원칙

1. **추론 노드와 실행 노드를 분리한다.** `planning` / `model_selection`(판단) /
   `critic` / `report`만 LLM을 호출합니다. `profiling`, `training`, `evaluate`는
   결정론적 코드입니다. 실행 노드에서 LLM이 코드를 생성하는 일은 없고, 미리 검증된
   [scripts/train.py](automl_agent/scripts/train.py)와
   [scripts/profile.py](automl_agent/scripts/profile.py)만 호출합니다. **학습은 LLM이
   시키지 않습니다** — LLM은 모델 이름과 하이퍼파라미터를 *제안*하고, 그 제안은
   레지스트리 화이트리스트와 클램프를 통과한 뒤에야 고정 스크립트의 config가 됩니다.
2. **LLM은 원본 데이터를 보지 않는다.** 원본 행을 여는 코드는 고정 스크립트
   세 개뿐이고, 그래프 안에 있는 둘([profile.py](automl_agent/scripts/profile.py),
   [train.py](automl_agent/scripts/train.py))은 subprocess로 돕니다. 세 번째
   [predict.py](automl_agent/scripts/predict.py)는 루프가 끝난 뒤의 명령이라 그래프에
   들어가지 않고 프롬프트를 만들지도 않습니다
   ([predict](#학습한-모델을-새-데이터에-쓰기--predict)). 프롬프트를 렌더링하는 프로세스는
   pandas를 import조차 하지 않습니다. [원본 데이터 경계](#원본-데이터-경계) 참조.
3. **루프 제어는 항상 코드가 갖는다.** 반복·종료·분기는
   [route()](automl_agent/graph.py#L27)와 그래프 엣지만 결정합니다. LLM에게 "이제
   멈춰야 할까?"를 묻지 않습니다. **목표 임계값도 묻지 않습니다** — 자기 기준선을
   스스로 정하게 하면 기준을 낮춰서 성공을 선언할 수 있습니다.
   [목표 임계값](#목표-임계값) 참조.
4. **학습은 언제나 별도 subprocess에서 돈다.** OOM/CUDA 오류가 오케스트레이터를
   죽이지 못하고, 프로세스 종료로 메모리가 완전히 회수되기 때문입니다.
   [nodes/training.py](automl_agent/nodes/training.py)는 얇은 wrapper로,
   `subprocess.run()` 후 결과 JSON만 파싱합니다. 학습 실패는 정상 흐름으로
   Critic에게 넘기며, 예외로 던져 실행을 중단시키지 않습니다.
5. **공유 State(blackboard)가 시스템의 심장이다.** 모든 시도가
   `history`(`operator.add` reducer)에 누적되고, 재시도 시 Planning이 그 이력을
   참고해 **이전과 다른 계획**을 만듭니다.
6. **Critic의 출력은 자유 텍스트가 아니라 구조화 스키마다.**
   `{failure_type, evidence, direction, concrete_changes}`이며 `failure_type`은 8종
   taxonomy로 제한됩니다.
7. **보고하는 숫자는 고르지 않은 숫자여야 한다.** 계획·하이퍼파라미터·`best` 선택은
   전부 검증 점수를 보고 이뤄지므로, 그 `best`를 실행의 결과로 인용하면 재지 않은
   폭만큼 과장됩니다. 그래서 [splits.py](automl_agent/scoring/splits.py)가 **첫 적합 전에**
   test 20%를 떼어 두고, 루프가 끝난 뒤 [nodes/holdout.py](automl_agent/nodes/holdout.py)가
   저장된 최고 모델로 그 행들을 **한 번만** 채점합니다.
   [채점 프로토콜](#채점-프로토콜--3분할과-반복-밖-1회-채점) 참조.
8. **차이를 원인이 있는 변화로 부르기 전에, 그 차이가 노이즈보다 큰지 밝힌다.** 모든
   점수는 한 슬라이스에 대한 점 추정이고 모든 판단은 그런 점수 두 개의 비교입니다.
   그래서 채점되는 분할마다 [intervals.py](automl_agent/scoring/intervals.py)가 95% 부트스트랩
   구간을 같이 내고, 그 구간 안에 들어오는 차이는 Critic·보고서·`holdout`이 "이 행들로는
   구분되지 않는다"고 이름을 붙입니다. 판정을 뒤집지는 않습니다 — 밝히기만 합니다.
   [부트스트랩 신뢰구간](#다시-뽑으면-얼마나-흔들리는가--부트스트랩-신뢰구간) 참조.

## 원본 데이터 경계

LLM에게 원본 행을 보이지 않는 것은 프롬프트에 "보지 마세요"라고 쓰는 방식으로는
지킬 수 없습니다. 채널과 프로세스로 나눕니다.

### 1. 구조로 (일차 방어)

| | 원본 행을 읽는가 | 무엇을 내보내는가 |
| --- | --- | --- |
| [scripts/profile.py](automl_agent/scripts/profile.py) | 읽음 (subprocess) | 카드 = 열 단위 집계 |
| [scripts/train.py](automl_agent/scripts/train.py) | 읽음 (subprocess) | metrics + status (+ `model.joblib`은 디스크에만) |
| [scripts/train.py --score-model](automl_agent/scripts/train.py) | 읽음 (subprocess) | test 분할 metrics — `holdout` 노드가 부릅니다 |
| [scripts/predict.py](automl_agent/scripts/predict.py) | 읽음 (그래프 밖) | 행 단위 예측 CSV — 사용자에게만 |
| 그 외 **모든** 노드 / `llm/client.py` | 읽지 않음 | — |

그래프 안의 두 스크립트는 LLM이 생성하지 않은 고정 코드이고, 항상 자식 프로세스로
돕니다. 따라서 **프롬프트를 렌더링하는 프로세스는 데이터 한 행도 메모리에 갖지
않습니다.**

`predict.py`도 고정 코드지만 그래프의 노드가 아닙니다 — 루프가 끝나고 사람이 부르는
명령이고, 출력이 행 단위라 어떤 state 채널에도 들어갈 수 없습니다. 그래서 이 표에서
유일하게 "무엇을 내보내는가"가 집계가 아닌 줄이고, 그 출력물은 `model.joblib`과 같은
등급으로 다뤄야 합니다([predict](#학습한-모델을-새-데이터에-쓰기--predict)).

State도 둘로 쪼갰습니다.

- `data_ref` — **비공개**. `{path, target_column}`. `profiling`과 `training`만
  읽습니다.
- `dataset_card` — **공개**. 집계뿐. 추론 노드 전부가 읽습니다.

카드가 데이터에서 추론으로 넘어가는 유일한 통로이고, 그 통로는 노드 경계입니다.
`result` 채널도 [privacy.public_result()](automl_agent/privacy.py)의 **화이트리스트**를
통과합니다 — 숫자 metric과 status만 남고, 셀 값이 섞일 수 있는 `log_tail`과 절대
경로가 담긴 `artifacts`는 state에 아예 들어가지 않습니다(디스크에는 남습니다).

**적합된 모델 파일도 데이터와 같은 급으로 취급합니다.** 매 iteration이
[model.joblib](#아티팩트-레이아웃)을 남기지만, SVC는 support vector를 그대로 담고
트리는 실제 값에서 읽은 분기점을 담습니다 — 모델 파일은 원본 행의 파생물입니다.
그래서 파일은 `.gitignore`가 막는 `artifacts/` 안에만 있고, `model_path`는
`PUBLIC_RESULT_FIELDS`에 **일부러 넣지 않았습니다**. state로 올라가는 것은 그 채점이
어느 분할에 대한 것인지 말하는 `split`(`"val"` | `"test"`) 하나뿐입니다.

같은 이유로 그 옆의 [feature_schema.json](#아티팩트-레이아웃)도, `predict`가 쓰는 예측
CSV도 같은 편에 있습니다 — 스키마는 범주 level과 클래스 라벨을 그대로 담고, 예측은
행마다 하나씩 나옵니다. `schema_path`도 `PUBLIC_RESULT_FIELDS` 밖입니다.

### 2. 카드의 방출 정책

`profile.py`는 열 전체에 대한 집계만, 그것도 **버킷**으로 냅니다.

| 낸다 | 내지 않는다 |
| --- | --- |
| 행/열 개수, 결측률, 클래스 비율 | 셀 값, 예시 행 |
| distinct/왜도/규모/상관 **버킷** | min·max·평균·표준편차·분위수 |
| 열 이름, dtype, 이상치 비율 | 클래스 라벨 이름 |
| 기준선 모델의 검증 분할 점수 | — |
| 그 점수들의 95% 부트스트랩 구간(`baseline.ci`) | — |
| 인코딩 결과(수치 N개 + one-hot M열, 제외된 열 **이름**) | 범주형 열의 **level 이름** |
| 기준선을 잰 분할 프로토콜(비율·시드·stratified) | — |

그리고 이 정책은 **allowlist로 강제**합니다. `privacy.validate_card()`가 카드의 최상위
키를 알려진 목록과 대조해서 모르는 키가 하나라도 있으면 실행을 중단하고, 그 아래는
재귀적으로 "모든 leaf는 숫자·문자열·불리언"인지 확인합니다. `public_card()`의
denylist는 최상위 이름만 봤기 때문에 `{"metadata": {"sample_rows": [...]}}` 같은 카드가
**그대로 프롬프트까지 갔습니다** — 감싸는 키 하나면 충분했습니다. 모르는 키를
통과시키지 않는 쪽으로 뒤집었고, `public_card()`는 2차 방어선으로 남겨 뒀습니다
(재개된 실행처럼 검증을 지나치는 경로에서도 비공개 `data` 블록은 떨어져 나가야
하니까요).

min/max 한 쌍은 **실재하는 두 환자의 값**입니다. 반면 플래너가 알아야 하는 것은
"이 열은 heavy-tailed이고 수백 단위"라는 사실이지 "3번 환자의 크레아티닌이
4.1"이라는 사실이 아닙니다. 기준선 점수가 정책에 맞는 이유는 학습 metric과
같습니다 — 9,400여 행의 검증 분할에 대한 점수는 집합 전체의 집계이지 한 레코드가
아닙니다. 그 점수의 신뢰구간도 같은 선 안쪽입니다: 경계값은 같은 분할을 400번 재표집한
**집계들의 백분위수**라서, min/max와 달리 어느 한 행의 값이 아닙니다. 클래스 비율은 내림차순으로 정렬해서 내보내므로 순서가
어느 라벨인지 알려주지 않습니다. 인코딩 보고서가 개수와 **제외된 열 이름**은 내면서
one-hot된 열의 **level 이름**은 내지 않는 것도 같은 선입니다 — 열 이름은 카드가 이미
dtype과 결측률까지 붙여 공개하는 것이지만, level 목록은 그 열의 **셀 값 전체**입니다
(`diagnosis` 열의 level을 다 적으면 그게 코호트의 진단 목록입니다).
카드 이름도 파일 이름이 아니라
`<target>-prediction`을 기본값으로 씁니다 — 파일 이름이 곧 데이터 출처이기 때문입니다.

### 3. 백스톱

`data_ref`를 추론 노드가 읽지 않는다는 것은 나중의 수정 한 줄로 조용히 깨질 수 있는
불변식입니다. 그래서 유일한 API 호출 지점에
[render_prompt()](automl_agent/llm/client.py) → `privacy.assert_clean()` 관문을 뒀습니다.
시스템의 모든 프롬프트는 이 함수를 통과합니다.

- **등록된** 데이터 경로가 프롬프트에 있으면 `RawDataLeak`을 던져 **실행을 중단**합니다.
  노드들은 이 예외를 잡지 않습니다 — 유출은 폴백으로 감출 버그가 아닙니다.
- 단지 경로처럼 *보이는* 문자열(LLM이 프롬프트에 되쓴 파일명 등)은 조용히
  마스킹합니다. false positive로 실행을 죽이는 편이 더 나쁩니다.
- 예외 메시지는 `scrub_message()`로 한 줄만 남깁니다. sklearn이
  `could not convert string to float: 'Male'`처럼 셀 값을 따옴표로 되돌려주기 때문에
  인용 리터럴은 마스킹하고, OOM·시간 근거가 되는 **숫자는 남깁니다**.
- 대가는 프롬프트 산문 쪽에 있습니다. `A/B`는 이 정규식에 절대 경로로 읽히므로
  `median/mean`이 `median<path>`로, `train/validation 격차`가 `train<path> 격차`로
  모델에 도착합니다. 관문을 느슨하게 하는 대신 **산문에서 슬래시를 피합니다** — 산문
  하나를 살리려고 정규식을 풀어서 실제 경로가 빠져나가는 것이 훨씬 나쁩니다. 프롬프트
  템플릿과 실행기 능력 목록, 규칙 기반 진단 문구가 이 관문을 통과해도 변형되지 않는지는
  개발 저장소의 `tests/test_privacy.py`와 `tests/test_critic.py`가 검사합니다.

### 4. 검증

개발 저장소 `tests/test_privacy.py`의 마지막 테스트가 실제 그래프를
**셀 값이 전부 canary 문자열인 CSV** 위에서 돌린 뒤, 그 실행이 남긴 프롬프트 전량과
state 채널 전체를 grep합니다. `--dry-run`에서도 프롬프트는 실제로 렌더링되어
저장되므로, 이것은 "모델에게 보냈을 바로 그 텍스트"를 검사하는 것입니다.
실제 CSV(47,144행 임상 코호트)로 돌린 실행에서도 파일 경로는 카드 원본·
`run_config.json`·`train/` 하위(즉 실행기 자신의 config와 로그)에만 있고, 아카이브된
9개 프롬프트 어디에도 없습니다. 같은 확인을 자기 데이터로 하려면:

```powershell
$files = Get-ChildItem artifacts\<id>\llm\* -File
"검사 대상 $($files.Count)개"          # 0개면 검증이 아니라 경로가 틀린 것
$files | Select-String -Pattern "<파일명>"   # 출력 없음이 정상
```

확장자를 걸지 않는 것과 파일 수를 먼저 찍는 것이 요점입니다. 실제 실행은 `.json`으로,
`--dry-run`은 `.dryrun.md`로 아카이브하므로 `*.md`로 좁히면 실제 실행에서는
**아무 파일도 검사하지 않고** "결과 없음"이 나옵니다 — 깨끗해 보이지만 검사한 게 없습니다.

아티팩트의 `structured_mode` 필드로 확인할 수 있습니다.

## 사용법

복사해서 쓰는 PowerShell 명령 모음은 [RUNBOOK.md](RUNBOOK.md)에 따로 정리했습니다.
데이터가 없다면 개발 저장소의 `examples/make_demo_data.py`로 `local/demo.csv`를 만들어 아래
`data.csv` 자리에 넣으면 됩니다 ([예시 데이터셋 카드](#예시-데이터셋-카드) 참조).
원본 데이터와 거기서 만든 카드는 [`local/`](#local)에 두세요 — git이 통째로 무시합니다.

```bash
# 원본 CSV에서 데이터셋 카드만 먼저 만들기 (사람이 읽고 고칠 수 있게)
# --metric/--margin 은 카드에 기록되지 않고, 그 설정으로 실행했을 때의
# 목표 임계값을 두 모드 모두 미리 보여주기만 합니다
python -m automl_agent.main profile \
  --data data.csv --target died \
  --metric roc_auc --margin 0.4 \
  --out local/my_card.json

# 새 실행 — 카드가 이미 있을 때 (기본 auto 모드: 카드의 기준선에서 목표를 도출)
python -m automl_agent.main run \
  --dataset-card examples/dataset_card.json \
  --metric f1 \
  --max-iterations 5 --time-budget-sec 3600 \
  --thread-id my-run-001

# 새 실행 — 원본 CSV에서 바로 (profiling 노드가 그래프 안에서 카드를 만듭니다)
python -m automl_agent.main run \
  --data data.csv --target died \
  --metric roc_auc \
  --thread-id my-run-002

# auto 모드에서 요구 수준만 올리기 (기준선에서 남은 여유의 50%)
python -m automl_agent.main run \
  --dataset-card local/my_card.json \
  --metric roc_auc --margin 0.5 \
  --thread-id my-run-003

# fixed 모드 — 배포 요구사항처럼 데이터 밖에서 온 숫자를 못박을 때
python -m automl_agent.main run \
  --dataset-card local/my_card.json \
  --metric roc_auc --goal-mode fixed --threshold 0.90 \
  --thread-id my-run-004

# 중단된 실행 재개 (다른 플래그 불필요 — run_config.json에서 복원)
python -m automl_agent.main resume --thread-id my-run-001

# 저장된 상태 확인 (--report 로 보고서 전문까지)
python -m automl_agent.main show --thread-id my-run-001 --report

# 끝난 실행이 고른 모델을 새 CSV에 적용 (iteration은 알아서 찾습니다)
python -m automl_agent.main predict \
  --thread-id my-run-001 \
  --data local/new_rows.csv --id-column patient_id \
  --out local/new_rows_predictions.csv

# 정답 열이 이미 있는 배치라면 채점까지 (예측은 위와 한 행도 다르지 않습니다)
python -m automl_agent.main predict \
  --thread-id my-run-001 \
  --data local/last_month.csv --id-column patient_id \
  --label-column outcome \
  --out local/last_month_predictions.csv

# 그래프 구조 저장
python -m automl_agent.main graph --out graph.png
```

반복마다 한 줄 요약을 출력합니다:

```
[iter 2] model=hist_gbdt f1=0.8100 (goal 0.85) → critic: hyperparam
```

### 주요 플래그

| 플래그 | 의미 |
| --- | --- |
| `--dataset-card` / `--data` | 둘 중 하나는 필수. 카드로 시작하거나, 원본 CSV로 시작합니다. |
| `--target` | 정답 컬럼. `--data`를 쓸 때 필수. |
| `--metric` | 목표 지표. 분류: `f1`, `accuracy`, `balanced_accuracy`, `precision`, `recall`, `roc_auc`, `pr_auc`. 회귀: `r2`, `mae`, `rmse`. 별칭은 `average_precision`→`pr_auc`, `mean_absolute_error`→`mae`, `root_mean_squared_error`→`rmse`, `r2_score`→`r2`. 목록은 [metrics.py](automl_agent/scoring/metrics.py) 한 곳에서 나오고, 여기에 없는 이름은 argparse가 거부합니다. 어느 쪽 목록에서 골라야 하는지는 정답 열이 결정합니다 — 카드의 task와 어긋나는 지표는 루프가 시작하기 전에 끊습니다. |
| `--on-missing-target` | 정답이 비어 있는 행의 처리. `reject`(기본, 개수를 알리고 중단) 또는 `drop`. `run`에서 생략하면 카드에 기록된 정책을 따릅니다. |
| `--goal-mode {auto,fixed}` | 목표 임계값을 정하는 방식. 기본 `auto`(카드의 기준선에서 도출). `--threshold`를 주면 `fixed`로 간주합니다. |
| `--threshold` | `fixed` 모드의 목표 임계값. `auto`와 함께 쓰면 거부합니다. |
| `--margin` | `auto` 모드에서 기준선의 남은 여유 중 목표로 삼을 비율(기본 `0.25`). `fixed`와 함께 쓰면 거부합니다. |
| `--dry-run` | LLM과 학습을 **모두** 모킹합니다. 자격 증명·학습 시간 없이 루프 전체를 검증합니다. (프로파일링은 실제로 돕니다) |
| `--scenario {success,fail,oom,stall,slow,crash}` | `--dry-run`에서 모의 학습이 따라갈 궤적. |
| `--no-llm` | 학습은 **실제로** 하고 추론 노드만 규칙 기반 폴백으로 돌립니다. 자격 증명 불필요. |
| `--force` | 같은 `--thread-id`의 기존 체크포인트를 삭제하고 처음부터 다시 실행합니다. |
| `--direction {maximize,minimize}` | 지표 최적화 방향. **지표가 이미 정하므로 생략이 기본입니다** — `mae`는 `minimize`, `f1`은 `maximize`. 지표가 함의하는 값과 다르게 주면 거부합니다(선호가 아니라 실수이므로). 같은 값을 주는 것은 확인용으로 허용합니다. |
| `--artifacts-root` | 아티팩트 루트 재지정(테스트용). |

`--force` 없이 이미 쓴 `thread_id`로 `run`을 다시 호출하면 거부합니다. 새 초기
state를 기존 스레드에 얹으면 `operator.add` reducer가 두 실행의 `history`를
이어붙여 조용히 섞기 때문입니다. 거부된 호출은 **아무것도 건드리지 않습니다** —
`run_config.json`은 체크포인트 검사를 통과한 뒤에 씁니다. 이전에는 검사보다 먼저
써서, 거부된 두 번째 `run`이 이미 기존 실행의 설정을 덮어썼고 나중의 `resume`이 새
설정을 옛 체크포인트에 대고 읽으며 그 반복들이 쓰지 않은 목표와 지표를
보고했습니다.

플래그 값 자체도 `RunConfig`가 검증합니다(`resume`이 `run_config.json`에서 이
객체를 재구성하므로 손으로 고친 파일에도 같은 가드가 걸립니다). `max_iterations=-1`은
루프를 건너뛰고 "반복 예산 소진"을 출력했고, `goal_margin=-2`는 기준선보다 *낮은* 바를
도출해 첫 시도에 성공을 선언했고, NaN `threshold`는 어떤 점수와도 비교되지 않아
`goal_met`을 영원히 False로 만들었습니다 — 모두 실행이 정상으로 *보이는* 값들이라
호출 시점에 끊습니다.

## 목표 임계값

`auto`(자동 조절)와 `fixed`(고정 지정) 두 모드가 있습니다.

| 모드 | 임계값 | 언제 쓰나 |
| --- | --- | --- |
| **`auto`** (기본) | 카드의 기준선에서 도출 | 데이터셋마다 "평범한 기본값을 유의미하게 이겼나"를 재고 싶을 때 |
| **`fixed`** | `--threshold` 값, 없으면 지표별 기본값 | 숫자가 데이터 밖에서 오는 경우 — 배포 요구사항, 이겨야 할 논문 점수, 규제 하한 |

`--goal-mode {auto,fixed}`로 고르고, `--threshold`만 주면 `fixed`로 간주합니다.
어느 쪽이든 **LLM에게는 임계값을 묻지 않습니다** — 모델이 자기 합격선을 정할 수 있으면
기준을 낮춰서 성공을 선언하는 것이 가장 쉬운 전략이 됩니다. 두 모드 모두 결정론적
코드입니다.

### 왜 두 개인가

고정된 `f1 >= 0.85`는 옮겨 쓸 수 없는 숫자입니다. 양성 11%인 임상 코호트에서는
모델이 아무리 좋아도 도달 불가이고, 잘 분리된 합성 카드에서는 공짜입니다. 어느
쪽이든 루프의 종료 조건은 "이 모델이 좋다"가 아니라 **"이 데이터셋이 쉽다"**를
재게 됩니다. 같은 데이터에서 `accuracy 0.85`는 더 나쁩니다 — 다수 클래스만 찍는
예측기가 0.89로 이미 넘습니다.

그렇다고 고정값이 틀린 것은 아닙니다. **숫자가 데이터 밖에서 올 때는 고정값이
정답**입니다. "0.90 미만은 배포 불가"라는 요구사항 앞에서 기준선 상대값은 의미가
없습니다. 서로 다른 일이라서, 하나의 heuristic이 둘 다 하려 들게 하지 않고 모드를
나눴습니다.

### `auto` — 기준선 상대

`profile.py`가 **고정된 기준선 모델**을 같은 데이터·같은 분할로 한 번
학습해 점수를 카드에 싣고, [goal.py](automl_agent/scoring/goal.py)가 그 점수에서 임계값을
도출합니다.

```
목표 = 기준선 + (1 - 기준선) × margin        (0~1 지표, maximize, margin 기본 0.25)
```

margin을 점수가 아니라 **남은 여유**에 적용하는 이유는 roc_auc의 마지막 0.05가
처음 0.05보다 훨씬 비싸기 때문입니다. 이렇게 하면 임계값의 *의미*가 데이터셋을
건너 같아집니다: **평범한 기본값을 유의미한 폭으로 이겨라.**

- 기준선: `LogisticRegression` + median 대치 + 표준화. train 60%에 적합해 **val 20%**에서
  잰 점수이고, `train.py`와 **같은 분할·같은 시드·같은 인코딩**이므로 모든 시도의 점수와
  직접 비교됩니다([채점 프로토콜](#채점-프로토콜--3분할과-반복-밖-1회-채점)). test 20%는
  프로파일링에서도 읽지 않습니다. 화려하지 않은 모델을 일부러 골랐습니다 — "이건 이미
  되는 수준"의 기준이어야 하니까요.
- `chance`: `DummyClassifier(strategy="prior")`를 같은 분할에서 잰 값. 기준선
  점수는 이것과 나란히 놓아야만 읽을 수 있습니다. 도출된 목표가 `chance + 0.02`
  보다 낮으면 그 선까지 끌어올립니다. `roc_auc`의 chance는 0.5, `pr_auc`의 chance는
  **양성 비율**입니다(상수 랭커의 average precision이 곧 양성 비율이므로).
- 상한 `0.99`: 완벽한 점수를 요구하면 항상 반복 예산으로 끝나서 진짜 정체가
  가려집니다. **다만 상한을 먼저 걸고 chance를 나중에 봅니다** — 순서가 반대였을 때
  다수 클래스가 99.5%인 코호트에서 `accuracy` 목표가 0.99, 즉 상수 예측기가 이미
  넘는 값으로 되돌아갔고, 실행은 아무것도 배우지 않은 채 목표 달성을 보고했습니다.
  chance가 상한을 밀어내면 목표는 `0.99`를 넘고, `goal.reference.exceeds_ceiling`이
  붙고, 배너와 보고서가 `(도달 불가)`로 표시하면서 `--metric balanced_accuracy`나
  `--metric pr_auc`로 바꾸라고 말합니다. 조용히 낮추지 않습니다.
- `minimize`(오차 지표 `mae`·`rmse`)는 반대로 `기준선 × (1 - margin)`, 상한 없는
  maximize 지표는 비례 상승 `기준선 × (1 + margin)`을 씁니다.
- `minimize` 쪽에도 위의 두 규칙이 거울처럼 걸립니다. **chance 규칙**: `Ridge` 기준선은
  평균 예측보다 *나쁠* 수 있고(음수 `r2`에는 chance보다 높은 `mae`가 따라옵니다) 그러면
  `기준선 × (1 - margin)`은 평균 예측기가 이미 넘는 바가 됩니다 — `chance × (1 - MIN_LIFT)`
  까지 **내려서** 조입니다(`lowered_to_clear_chance`). 두 방향이 공유하는 불변식은
  하나입니다: 보정은 목표를 더 어렵게만 만듭니다. **상한 규칙**: 바가 `0` 이하로
  떨어지면(`--margin 1.0`, 또는 기준선이 이미 오차 0) 그것은 정확한 예측을 요구하는 바이고,
  `goal.reference.demands_zero_error`가 붙고 배너가 `(도달 불가)`로 표시합니다. 여기서
  고칠 것은 지표가 아니라 margin이라서 `exceeds_ceiling`과 문구가 다릅니다 — `mae`는
  재기에 맞는 지표이고, `--margin`을 1보다 작게 두거나 실제 허용 오차를
  `--goal-mode fixed --threshold`로 직접 주라고 말합니다.

개발 저장소의 `make_demo_data.py`로 만든 카드에서 두 모드가 내는 값
(8,000행, 양성 12.5%):

| 지표 | chance | 기준선(logreg) | `auto` 목표 | `fixed` 기본값 |
| --- | --- | --- | --- | --- |
| `roc_auc` | 0.5 | 0.7444 | **0.8083** | 0.90 (이 데이터에서 도달 불가) |
| `f1` | 0.0 | 0.3108 | **0.4831** | 0.85 (12.5% 유병률에서 불가능) |
| `accuracy` | 0.8744 | 0.8919 | **0.9189** | 0.85 (다수 클래스가 이미 넘음) |
| `balanced_accuracy` | 0.5 | 0.5931 | **0.6948** | 0.80 |
| `pr_auc` | 0.1256 | 0.4851 | **0.6138** | 0.70 |

`--metric`이 받는 이름은 [metrics.py](automl_agent/scoring/metrics.py)의 레지스트리 하나에서
나옵니다. 목표 임계값·프로파일러의 기준선 점수·학습기가 내는 metric이 모두 이 목록을
읽습니다. 세 곳이 각자 목록을 들고 있던 동안 `--metric balanced_accuracy`는 임계값도
도출되고 기준선도 측정됐지만 학습기가 그 키를 만들지 않아서 `goal_met`이 없는 점수를
비교했고, 모든 반복에서 조용히 False였습니다.

레지스트리에는 회귀 지표(`r2`, `mae`, `rmse`)도 있고, 각 항목이 자기 **task**와
**방향**을 함께 선언합니다. 둘 다 지표의 속성이지 호출자의 선택이 아닙니다 — 연속 열을
`f1`로 채점할 수는 없고, `mae`를 maximize하는 것은 선호가 아니라 실수입니다. task는
정답 열에서 읽히고(`targets.detect_task`) 카드에 기록되므로, 카드의 task와 어긋나는
`--metric`은 루프가 시작하기 전에 profiling 노드가 끊고 그 열에서 쓸 수 있는 지표를
열거해 줍니다. `mae`·`rmse`는 `fixed` 기본값이 **없습니다**: 정답 열의 단위로 나오는
지표에 이식 가능한 기본 바는 존재하지 않고, `0.85`를 넣으면 모델이 아니라 그 열의 단위에
대한 바가 됩니다. 그 둘은 `--threshold`나 측정된 기준선을 요구합니다.

`profile` 명령이 카드를 만든 뒤 이 두 줄을 나란히 출력하므로, 실행 전에 어느 모드를
쓸지 보고 결정할 수 있습니다. `--margin`도 받으므로 요구 수준을 올렸을 때의 바를
실행을 쓰지 않고 확인할 수 있습니다 — margin은 점수가 아니라 남은 여유에 걸리기
때문에 같은 증분이 데이터셋마다 다른 폭으로 움직이고, 머릿속 환산이 안 됩니다.

```
--margin 0.25 → roc_auc 0.8083   (기준선 0.7444)
--margin 0.40 → roc_auc 0.8466
--margin 0.50 → roc_auc 0.8722
```

같은 +0.1 margin이 여기서는 바를 0.026 올리지만 기준선이 0.83인 데이터에서는 0.017밖에
올리지 않습니다. 그래서 "0.9 정도를 요구하려면 margin을 얼마로?"는 카드마다 다른 답을
가지고, 미리보기 없이는 맞출 수 없습니다.

기준선이 없는 카드(손으로 쓴 카드, `--no-baseline`)에서 `auto`는 지표별 기본값으로
폴백하고 **경고를 출력합니다** — 재지 않은 숫자를 잰 것처럼 보이게 하지 않습니다.

### `fixed` — 밖에서 온 숫자

`--threshold`가 곧 목표이고, 데이터의 어떤 것도 그 값을 움직이지 못합니다.
`--goal-mode fixed`만 주고 값을 생략하면 지표별 기본값(`f1` 0.85, `roc_auc` 0.90 …)을
씁니다. 기준선은 이 모드에서도 **여전히 측정합니다** — 플래너가 "선형 모델은 이미
0.83을 낸다"를 아는 것은 목표와 별개로 유용하고, 카드가 모드에 따라 달라지지 않는
편이 낫기 때문입니다.

### 모순되는 조합은 거부한다

조용히 무시된 플래그가 최악입니다 — 아무도 요구하지 않은 기준으로 성공/실패를
보고하게 됩니다.

| 명령 | 결과 |
| --- | --- |
| `--threshold 0.9` | `fixed` 모드 (값을 준 것이 곧 모드 선택) |
| `--goal-mode auto --threshold 0.9` | **거부** — auto는 스스로 도출하므로 값을 받을 자리가 없습니다 |
| `--goal-mode fixed --margin 0.5` | **거부** — `--margin`은 auto에서만 의미가 있습니다 |
| `--margin 0.5` | `auto` 모드, 남은 여유의 50%를 요구 |

### `goal` 채널

두 모드가 같은 모양을 냅니다. 노드들은 어느 모드가 만든 값인지 몰라도 됩니다.
`initial_state`가 먼저 심고, `auto`에서는 `profiling` 노드가 기준선을 측정한 뒤
덮어씁니다.

```json
{"metric": "roc_auc", "direction": "maximize", "mode": "auto",
 "threshold": 0.872, "source": "derived",
 "reference": {"source": "baseline", "metric": "roc_auc", "baseline": 0.8294,
               "margin": 0.25, "chance": 0.5}}

{"metric": "roc_auc", "direction": "maximize", "mode": "fixed",
 "threshold": 0.9, "source": "fixed"}
```

`source`는 네 값 중 하나입니다: `derived`(auto, 기준선에서) · `fallback`(auto인데
기준선이 없음) · `fixed`(직접 지정) · `fixed_default`(지표 기본값). 보고서와 CLI가
이 값을 그대로 문장으로 옮기므로, 0.872가 보편적 기준인 것처럼 읽히지 않습니다.

## 채점 프로토콜 — 3분할과 반복 밖 1회 채점

분할은 [splits.py](automl_agent/scoring/splits.py) 한 곳에서 나오고, `profile.py`와 `train.py`가
같은 함수를 부릅니다.

```
전체 행 ─┬─ test  20%   ← 가장 먼저 떼어 둡니다. 루프가 끝날 때까지 아무도 읽지 않습니다
         └─ 나머지 80% ─┬─ train 60%   기준선과 모든 시도가 적합하는 행
                        └─ val   20%   기준선 점수·매 시도 점수·`best` 선택이 나오는 행
```

세 분할 모두 stratified이고 `--seed`만 받습니다. 즉 **test 행은 (파일, 시드)의 함수**라서
같은 실행의 모든 iteration이, 그리고 프로파일러와 학습기라는 서로 다른 두 프로세스가
정확히 같은 행을 떼어 둡니다. 인덱스를 저장하지 않고 매번 다시 계산하는데, 저장한 값이
어긋날 수 있는 것보다 다시 계산해서 같아지는 편이 검증 가능합니다
(개발 저장소의 `tests/test_splits.py`가 disjoint·재현성·클래스 비율을 성질로
검사합니다).

### 왜 세 개인가 — `best`는 최댓값이라 편향되어 있습니다

5회 반복이면 `best`는 **노이즈가 섞인 검증 점수 5개의 최댓값**입니다. 계획도,
하이퍼파라미터도, 어느 시도를 `best`로 삼을지도 전부 그 숫자를 보고 정했습니다. 그런데
보고서는 같은 숫자를 실행의 결과로 인용했습니다 — 재지 않은 폭만큼 과장한 것이고,
반복이 늘수록 커집니다.

`holdout` 노드가 그 폭을 잽니다. 실제 측정값(demo.csv, `--no-llm`):

| 실행 | 반복 | 검증 `best` | test | `selection_gap` |
| --- | --- | --- | --- | --- |
| `auto`(→ 0.8083) | 1회에 달성 | 0.8545 | 0.8427 | **+0.0119** |
| `fixed` 0.90 | 3회 소진 | 0.8648 | 0.8412 | **+0.0236** |

같은 데이터·같은 모델 계열인데 시도를 3개 놓고 최댓값을 고르자 격차가 두 배가 됐습니다.
`selection_gap`이 곧 유보 조건의 크기이고, 지표 자신의 단위로 나옵니다.

### 어디에 놓여 있는가 — `route()` **다음**

```
evaluate ──route()──► "report" ──► [holdout] ──► [report] ──► END
             │
             └──────► "critic" ──► planning …          (루프 안에서는 test를 읽지 않습니다)
```

일부러 종료 판단 **뒤**입니다. test 점수가 루프의 행동을 바꿀 수 있으면 그건 더 이상 떼어
둔 숫자가 아닙니다. 같은 이유로 결과를 `result` 채널에 합치지 않고 `holdout` 채널을
따로 씁니다 — `route()`와 `goal_met`이 읽는 채널이니까요. 목표 달성 판정은 여전히 검증
점수로만 합니다.

### 어떻게 채점하는가 — 재적합하지 않습니다

매 iteration이 적합한 파이프라인을 `model.joblib`으로 남기고
([config.MODEL_FILENAME](automl_agent/config.py)), `holdout` 노드는 **최고 성능
iteration의 그 파일과 그 iteration의 `train_config.json`**을 그대로 써서
`train.py --score-model`을 부릅니다. 재적합하면 그건 다른 모델의 점수입니다.
채점은 `evaluate_split()` 하나가 하므로, 보고서가 나란히 놓는 두 숫자는 **다른 행에 대해
같은 코드로** 계산된 값입니다.

```bash
python -m automl_agent.scripts.train --config <iter의 train_config.json> \
  --out <run_dir>/holdout.json --score-model <iter의 model.joblib>
```

### 없으면 없다고 씁니다

`--dry-run`, 모든 시도가 실패한 실행, 모델을 저장하기 전 버전의 실행, 채점 자체가 실패한
경우 — 네 경우 모두 `{"status": "skipped", "reason": ...}`를 남기고 보고서는 그 사유를
적습니다. 최종 측정이 없다고 보고서를 안 쓰면 실행이 실제로 모은 근거를 버리게 됩니다.

### 카드의 프로토콜이 실행과 어긋나면 거부합니다

`auto` 모드의 바는 카드의 기준선에서 나오므로, 그 기준선이 **다른 행**에서 측정된 것이면
바와 점수가 서로 다른 규칙으로 매겨진 숫자입니다. 그래서 카드의 `baseline.protocol`이
실행 설정과 다르면 `ProfilingFailed`로 멈춥니다 — `--on-missing-target`에 대해 지키는 규칙과
같은 이유입니다 — "기준선을 잰 데이터와 학습이 점수를 내는 데이터가 같아야 한다"
([splits.py](automl_agent/scoring/splits.py)의 `protocol_mismatch`). `protocol` 블록이 **아예 없는** 카드는
그 필드보다 앞선 것이므로 받아들입니다.

```json
"protocol": {"train_fraction": 0.6, "val_fraction": 0.2, "test_fraction": 0.2,
             "stratified": true, "seed": 42}
```

## 다시 뽑으면 얼마나 흔들리는가 — 부트스트랩 신뢰구간

위 절의 `selection_gap`이 "최댓값을 골랐다"는 편향을 재는 동안 질문이 하나 남습니다:
그 **한 번의 측정 자체**가 검증 행을 다시 뽑으면 얼마나 움직이는가. MIMIC 표본의 검증
분할은 2,400여 행에 양성 290개 정도라서 `f1`이 재표집만으로 ±0.03 흔들립니다.
0.7412 → 0.7503을 "개선됨"으로 보고한 실행은 그 재표집을 보고한 것이고, 실제 실행
하나가 그 폭 안에서 네 번을 걸었습니다.

그래서 채점되는 모든 분할이 목표 지표에 대해 **95% percentile 부트스트랩 구간**을 같이
냅니다 ([intervals.py](automl_agent/scoring/intervals.py), 재표집 400회). 비교를 만드는 소비자
쪽에서는 자기가 찾은 차이가 그 구간 안에 들어가는지를 말합니다 — `holdout`은
선택 편향에 대해, 보고서는 자기 대표 숫자에 대해. **iteration 간 움직임은 예외입니다** —
같은 행에서 채점된 두 시도이므로 아래의 짝지은 구간이 그 자리를 대신합니다.

### 편향과 다른 양입니다

| | 무엇을 재는가 | 어디서 나오는가 | 방향 |
| --- | --- | --- | --- |
| `selection_gap` | 검증 점수 5개의 최댓값을 골랐다는 편향 | 떼어 둔 test 분할 1회 채점 | 한쪽(과대평가) |
| 신뢰구간 | 이 행들에 대한 **한 번의** 측정의 표집 노이즈 | 같은 분할의 재표집 400회 | 양쪽 |

두 값을 더하지도, 하나로 다른 하나를 대체하지도 않습니다. 그리고 두 시도의 구간이
겹친다는 것은 "이 행들이 두 모델을 구분하지 못한다"는 뜻이지 "두 모델이 같다"는 뜻이
아닙니다. train 분할 점수에는 일부러 구간을 붙이지 않았습니다 — in-sample 점수의
불확실성은 이 폭이 설명하는 것이 아니고, Critic이 train 숫자를 읽는 이유는 노이즈가
아니라 `train_val_gap`이기 때문입니다.

### 두 시도를 비교할 때는 짝지은 구간입니다

위의 구간은 **한 점수**가 얼마나 흔들리는지를 재는 폭이라서, 두 시도의 차이에 대고 쓰면
너무 넓습니다. 두 시도는 같은 검증 행에서 채점되므로 "이 행이 원래 어려웠다"는 몫이 두
점수에 똑같이 실려 있고, 차이를 보면 그 몫이 상쇄됩니다. 그래서 행별 예측을 짝지어
재표집합니다 ([`paired_delta`](automl_agent/scoring/intervals.py), 재표집 400회, 같은 95%):

| 무엇을 비교하나 | 어느 폭인가 | MIMIC 표본의 반폭(`balanced_accuracy`) |
| --- | --- | --- |
| 시도 하나의 점수 자체 | 주변부(marginal) 구간 | 0.013~0.014 |
| 시도 A와 시도 B의 차이 | 짝지은(paired) 구간 | **0.0061** |

가운데 띠가 이 구별이 값을 하는 구간입니다 — |Δ|가 대략 0.006~0.013이면 주변부로는 "구분
안 됨", 짝지은 구간으로는 "구분됨"입니다. 전처리 레버가 내는 크기가 정확히 그 안에 들어
앉습니다.

짝을 맞췄다는 것은 검사해야 하는 전제입니다. 학습 스크립트가 검증 슬라이스의
`val_fingerprint`([splits.py](automl_agent/scoring/splits.py))를 예측과 함께 저장하고, 지문이
다르면 짝지은 검정을 내지 않고 `split_changed`를 냅니다 — 행이 바뀐 두 벡터를 짝지어 놓고
좁은 구간을 내는 것이 여기서 유일하게 나쁜 결말이라서요.

**고치는 것은 해상도이고 교란은 고치지 않습니다.** 계열과 전처리가 같은 전이에서 함께
움직였으면 짝지은 Δ는 그 합을 좁은 구간으로 잴 뿐이고, 어느 쪽 몫인지는 말하지 않습니다.

### 조종과 수락은 다른 판정선입니다

두 판정이 서로 다른 비용을 지므로 폭도 다릅니다.

| | 무엇을 정하는가 | 어느 채널 | 오판의 값 |
| --- | --- | --- | --- |
| 조종 | 다음에 무엇을 처방할지 | 루프 안의 짝지은 구간 | iteration 하나 |
| 수락 | "이 실행이 개선했다"는 보고 | 떼어 둔 test 1회 채점(`holdout`) | 실행의 결론 |

민감한 쪽을 조종에 두는 것이 요점입니다. **그리고 수락은 우승 확정의 게이트가 아닙니다.**
test 점수가 `best`를 고르거나 확정하거나 뒤집는 데 한 번이라도 쓰이면 test 20%가 선택
집합의 일부가 되고, `capabilities._CLASSIFICATION_SCORING`이 모든 계획에 대고 하는 약속
— 먼저 떼어 두고, 루프가 끝난 뒤 딱 한 번 채점하고, 계획이나 진단에는 절대 보이지 않는다
— 이 그 순간부터 거짓이 되며, 그 대가를 잴 수단은 실행 안에 남아 있지 않습니다. 게이트가
필요하면 네 번째 분할이나 반복 CV여야 합니다.

민감함의 값은 다중성입니다. 반폭 0.0061짜리 판정선을 한 실행의 4회 비교에 적용하면 귀무
아래 **기대 거짓양성 0.2건**이고, 기대값은 비교들의 상관에 불변입니다. 최소 1건이 뜰 확률은
완전 양의 상관에서 0.05, 독립에서 0.186이며 **독립이 상한 쪽**입니다 — 루프에 유리한 쪽을
가정으로 깔지 않으려고 이렇게 적습니다. 코드는 이것을 보정하지 않습니다. 보정하면 조종이
둔해지고, 조종은 민감해도 되는 자리입니다.

`selection_gap` 0.0078이 이 논거를 대체하지는 않습니다. 그것은 선택 효과의 **단일 실현의
크기**이고 다중성은 **비율**입니다 — 한 실행의 작은 gap은 민감한 판정선이 노이즈에 얼마나
자주 걸리는지에 대해 아무것도 말하지 않고, 두 숫자는 어느 방향으로도 서로를 대신하지
못합니다.

### 그룹 분할이면 그룹을 재표집합니다

환자당 방문 5회가 들어 있는 분할을 행 단위로 재표집하면 독립 관측이 `5 × 환자수`개
있는 것처럼 계산해서 구간이 좁게 나옵니다 — 부풀린 점수를 자신 있는 점수로 바꿔 놓는
것뿐이라, [splits.py](automl_agent/scoring/splits.py)가 분할에 대해 닫은 구멍을 재표집에서
다시 열게 됩니다. 같은 파일(환자 150명 × 방문 5회, feature는 노이즈, 라벨은 환자별로
부여)을 두 프로토콜로 채점한 로그:

| 분할 | 재표집 단위 | `f1` | 95% CI | 폭 |
| --- | --- | --- | --- | --- |
| 그룹(`--group-column subject_id`) | group 400회 | 0.3472 | 0.0833~0.5556 | **0.4723** |
| 행 | row 400회 | 0.9697 | 0.9426~0.9925 | **0.0499** |

아래 줄이 아홉 배 더 확신에 차 있지만 정답은 위 줄입니다 — feature가 노이즈이므로
정직한 점수는 우연 수준입니다. **좁은 구간은 프로토콜이 맞다는 증거가 아닙니다.** 구간은
분할이 정한 규칙 안에서의 폭이라서, 잘못된 분할은 잘못된 숫자를 좁게 감쌉니다.

### 어디에 실려 나오는가

| 채널 | 키 |
| --- | --- |
| 매 시도의 결과 | `metrics.<metric>_ci_low` / `metrics.<metric>_ci_high` |
| 카드의 기준선 | `baseline.ci.scores.<metric>.{low,high}`, `baseline.ci.{level,unit,resamples}` |
| `auto` 모드의 바 | `goal.reference.baseline_ci`, `baseline_ci_unit`, `inside_baseline_ci` |
| 최종 홀드아웃 | `holdout.score_ci`, `holdout.val_inside_ci` |
| 매 시도의 짝지은 비교 | `paired.{status,metric,baseline_iteration,delta_vs_best,delta_ci_low,delta_ci_high,p_better,resamples,unit}` |
| Critic 프롬프트 | `## What these rows can resolve` 절 + 진단 규칙 9 |
| Critic 프롬프트 (레저) | `## What each prescription was worth` 절 — 행마다 `짝지은 Δ`와 그 CI, 없는 행은 `짝지은 검정 없음` |
| 보고서 | 요약 문장의 점수 옆, 프롬프트의 `## Full attempt history` 해설 |

카드는 `--metric`이 정해지기 전에 쓰이므로 **레지스트리의 모든 지표**에 대해 구간을
냅니다. 어차피 그중 하나가 `auto` 모드에서 바가 되고, 여기서 구간이 값을 합니다 —
자기가 파생된 점수의 구간 안에 들어앉은 바는 이 데이터셋 검증 슬라이스의 노이즈 바닥
안에 있는 바이고, `goal.describe()`가 반복이 시작되기 **전에** 그렇게 적습니다.

### 밝히기만 하고 막지 않습니다

목표 달성 판정은 여전히 점수와 바의 비교 하나입니다. 구간이 바를 삼켜도 판정을 뒤집거나
실행을 멈추지 않고, 보고서와 `goal.describe()`가 그 사실을 적으면서 `--margin`을 키우는
쪽을 가리킵니다. 시도가 바를 넘었다고 아무것도 배우지 않은 것은 아니기 때문입니다 —
시도는 기준선과 **같은 행**에서 채점되므로 두 오차가 같이 움직이고, 짝지은 비교는 어느
쪽 구간보다도 좁습니다. 정직한 읽기는 "이 마진은 이 슬라이스의 노이즈 바닥에 있다"이고,
그것을 정리하는 숫자는 떼어 둔 test 점수입니다.

끄는 CLI 플래그는 없습니다. `train.py`는 config의 `bootstrap.resamples`만 읽고(`0`이면
구간 없음), 50만 행 분할을 가진 호출자를 위한 탈출구로만 남겨 뒀습니다 — 구간은
"개선됨"과 "이 행들로는 구분되지 않음"을 가르는 값이라서, 플래그를 만들면 실행을 결단력
있어 보이게 하려고 끄게 됩니다.

### 없으면 없다고 씁니다

재표집 단위(행, 또는 그룹 분할이면 그룹)가 **20개 미만**이거나 재표집의 20% 이상이
계산에 실패하면 구간을 내지 않고 로그에 사유를 적습니다
(`f1: no confidence interval (split too small, or metric degenerate)`). 15행에서 뽑은
구간은 넓고 옳고 쓸모없으며, 환자 4명에서 뽑은 구간의 백분위수는 그 네 값 자체입니다.
구간이 없는 실행(예전 실행, 재개된 스레드, 작은 슬라이스)에서 보고서와 `holdout` 줄은
예전처럼 점수만 적습니다. Critic 프롬프트만 **구간이 없다고 말하는 문장**을 채워
넣습니다 — 그 절은 템플릿에 항상 있고, 비어 있는 절은 "불확실성 없음"으로 읽히니까요.

## 범주형 열 — `features.py`

두 스크립트가 `select_dtypes(include=["number", "bool"])`로 문자열 열을 전부 버리고
있었습니다. MIMIC 표본에서는 14열 전부 수치라 대가가 0이었지만, 보통의 업무용 표에서는
신호의 대부분을 버립니다. [features.py](automl_agent/dataset/features.py)의 `encode_features`
하나가 두 스크립트 몫을 다 합니다 — 프로파일러의 기준선과 학습기의 시도가 **같은 행렬**을
봐야 한다는 것이 분할과 같은 논리입니다.

| 열 | 처리 |
| --- | --- |
| 수치·불리언 | 그대로 |
| 고유값 ≤ 50인 문자열/범주형 | **one-hot** (level 이름 정렬 순, 결측은 자기 level `<missing>`) |
| 고유값 > 50 | 제외하고 **이름을 알립니다** |
| datetime 등 | 제외하고 이름을 알립니다 |

- **ordinal이 아니라 one-hot입니다.** ordinal 코드는 데이터에 없는 순서를 발명합니다.
  트리는 어느 정도 우회하지만 선형 기준선은 못 하고, **그 기준선이 바의 출처**라서
  인코딩의 부산물로 바가 움직이게 됩니다.
- **결측은 자기 level입니다.** 범주형에서 "없음"은 보통 그 레코드에 대한 사실이고,
  대안(전부 0인 행)은 인코더가 본 적 없는 범주와 구별되지 않습니다. 정답 컬럼에
  적용하는 규칙([targets.py](automl_agent/dataset/targets.py))과 정반대인데, 그쪽에서 발명된
  클래스는 아무도 부여하지 않은 라벨이기 때문입니다.
- **level 집합은 전체 행에서 학습합니다.** 의도적이고 범위가 좁습니다 — 특성 값만 쓰고
  정답은 보지 않으므로, 홀드아웃에서 임계값을 고르는 것과 달리 점수를 부풀릴 수
  없습니다. 대가로 얻는 것은 인코딩된 행렬이 파일의 순수 함수라는 것입니다. 실제로
  누출될 통계(대치 median, 스케일러의 평균·분산)는 추정기 파이프라인 안에 있고 여전히
  train 행에서만 적합됩니다.

카드에는 개수와 **제외된 열 이름**만 실립니다. one-hot된 열의 level 이름은
[내지 않습니다](#2-카드의-방출-정책).

## 학습한 모델을 새 데이터에 쓰기 — `predict`

바로 위 문단이 자랑하는 성질("인코딩된 행렬은 파일의 순수 함수")이 그대로 결함이었습니다.
**level 집합, 열 순서, `<missing>` 열의 유무는 모두 인코더 앞에 놓인 행들이 정합니다.**
그래서 같은 함수에 두 번째 파일을 주면 다른 행렬이 나옵니다 — 어떤 level이 이번 배치에
없으면 열이 하나 사라지고, 새 범주가 들어오면 열이 생기지 않고, 열 순서는 새 파일을
따릅니다. 그런데 `model.joblib`은 저장되고 **그 모델을 만든 인코딩은 저장되지 않았습니다.**
`predict` 서브커맨드도 없었습니다.

폭이 다르면 sklearn이 막습니다. 문제는 **폭이 맞는 경우**입니다.

### 조용히 어긋나는 경우 — 측정치

900행 · `hist_gbdt` · `city ∈ {seoul, busan, daegu}`로 적합한 뒤, 지역 코드 체계가 바뀌어
`seoul`이 `incheon`으로 재코딩된 새 배치 200행에 적용해 봤습니다. 스키마 없이 새 파일에서
인코딩을 다시 유도하면:

| | `city`에서 나온 세 열 | 전체 폭 |
| --- | --- | --- |
| 다시 유도한 인코딩 | `city=busan`, `city=daegu`, `city=incheon` | 9 |
| 학습 때의 인코딩 | `city=busan`, `city=daegu`, `city=seoul` | 9 |

폭이 9로 같으니 **예외가 나지 않습니다.** `city=incheon`이 모델이 `city=seoul`로 학습한
칸에 들어갑니다. 결과: **예측 라벨이 200행 중 19행에서 뒤집혔고**, 평균 |Δp| 0.089,
최대 0.6439. 오류도, 경고도 없고, 이것을 보여줄 지표도 없습니다 — 예측이 필요한 행에는
정답이 없으니까요.

### 고친 방법

인코딩을 **적합 시점에 저장하고**, 예측할 때 그 저장본을 재생합니다.

- `features.py`가 두 함수로 갈렸습니다. `build_schema`가 레이아웃을 적합하고,
  `encode_with_schema`가 **이미 있는** 레이아웃을 적용합니다. `encode_features`는 이 둘을
  이어 붙인 것이라, 자기 파일을 소유한 두 호출자(프로파일러와 각 학습 시도)에게는 아무것도
  바뀌지 않았습니다 — `test_splitting_fit_from_transform_did_not_change_what_encoding_produces`가
  이 동일성을 고정합니다.
- `scripts/train.py`가 `model.joblib` 옆에 `feature_schema.json`을 씁니다. `save_model`과
  같은 규칙으로 **치명적이지 않습니다**: 점수는 이미 벌어 놓은 것이라 디스크가 찼다고
  실행을 잃는 게 더 나쁜 실패입니다.
- `scripts/predict.py`가 새로 생겼습니다. `main.py predict`가 이 실행이 선택한 iteration을
  스스로 찾아 두 파일을 짝으로 읽습니다.
- **홀드아웃 채점도 저장된 스키마를 씁니다.** 평소에는 다시 유도한 것과 같은 답이 나오고,
  다른 답이 나오는 경우가 바로 잡아야 할 경우입니다 — 적합과 홀드아웃 사이에 파일이 편집된
  실행. 스키마가 없는 옛 실행은 예전 방식으로 채점하고 로그에 그렇게 적습니다.
- **스키마는 레이아웃만 담지 않습니다.** 레이아웃이 맞는 것과 배치가 비교 가능한 것은 다른
  이야기이고, 그 틈이 벌어지는 두 경로는 둘 다 폭 검사에 안 보입니다: 모델을 unpickle할
  **라이브러리 버전**(`environment`)과 열이 실제로 담고 있던 것(`column_stats` — 수치 열별
  결측률과 `-9999` 같은 결측 코드의 비율). 둘 다 적합 때 기록하고, 재생할 때 대조하고,
  **알리기만** 합니다. 대조는 `encode_with_schema`가 하므로 나중에 어떤 재생 경로가
  생기더라도 이 검사를 공짜로 받습니다 — 인코더가 둘이 아니라 하나인 것과 같은 이유입니다.
- **`SCHEMA_VERSION`은 1에서 2가 되었고, 읽기 규칙은 비대칭입니다.** 더 낮은 version은 받아
  주고 그 version에 없던 검사를 이름으로 적어 알립니다("라이브러리 버전 대조를 하지
  못했습니다 … 위에 없는 항목은 이상이 없다는 뜻이 아니라 검사하지 않았다는 뜻입니다").
  거부는 **더 높은** version에만 남습니다. 어제 학습한 모델을 오늘 못 쓰게 만드는 쪽이 더
  나쁜 실패입니다.

### 무엇을 거부하고 무엇을 알리기만 하는가

거부(예측이 나오지 않습니다):

| 상황 | 왜 |
| --- | --- |
| 모델이 필요한 원본 열이 새 파일에 없음 | 대안이 전부 조용합니다 — 전부 NaN인 열을 만들면 대치기가 없는 특성의 값을 발명하고, 새 파일이 주는 열에 맞춰 재정렬하면 뜻이 다른 열로 채운 정상 폭 행렬이 나옵니다 |
| `feature_schema.json`이 없음 | 인코딩 자체가 남아 있지 않으므로 유도하지 않고 그렇게 말합니다. 합성 데이터 실행과 이 파일이 저장되기 전 버전의 실행이 여기 해당합니다 |
| 스키마 version이 이 빌드보다 **새로움** | 모르는 레이아웃을 추측하는 것이 위 표의 사고로 가는 길입니다. 반대 방향(더 **낮은** version)은 거부하지 않습니다 — 어제 학습한 모델을 오늘 못 쓰게 만드는 쪽이 더 나쁩니다. 대신 그 version에 없던 검사를 **이름으로** 적어서 알립니다 |
| `--label-column`이 가리키는 열이 새 파일에 없음 | 채점해 달라는 요청이 조용히 예측만 하고 끝나면 묻지 않은 질문에 답한 것이 됩니다 |
| 조립된 폭이 추정기의 `n_features_in_`과 다름 | 인코더와 스키마는 항상 서로 일치합니다(같은 함수가 씁니다). 이 검사는 **두 파일이 같은 적합에서 나왔는지**를 봅니다 — 디렉터리가 증명해 주지 못하는 유일한 것 |

알리기만 (예측은 나오고, 한 줄씩 한글로 출력됩니다):

| 상황 | 인코딩 | 왜 막지 않는가 |
| --- | --- | --- |
| 학습 때 없던 범주 | 그 열의 모든 level 열이 0 | 학습 때 그 level에 열이 없었다면 나왔을 바로 그 행입니다 |
| 학습 데이터에 결측이 없던 열에 결측 | 전부 0 (`<missing>` 열이 적합되지 않았음) | 같은 이유. 새 행들이 학습 행들에 없던 구멍을 가졌다는 사실은 알려야 합니다 |
| 수치 열이 텍스트가 되어 있음 | 파싱 실패 셀만 NaN, 행 수를 셈 | 100만 행 중 한 셀이 이상하다고 거부하는 건 과합니다. 열 전체가 텍스트가 된 경우와는 개수가 구분해 줍니다 |
| 학습 파일에 없던 열 / 학습 때도 제외됐던 열 | 무시 | 모델이 쓸 수 없습니다. 다만 "당신이 추가한 열"과 "애초에 쓰지 못한 열"은 다른 실수라 따로 셉니다 |
| 모델을 unpickle할 라이브러리 버전이 적합 때와 다름 | 그대로 실행 | 대개는 아무 일도 없고, 거부하면 정상 조합까지 막습니다. 다만 sklearn이 pickle 호환을 보장하지 않으므로 **조용한 실패의 후보 목록**으로 한 줄 남깁니다 (`numpy`·`pandas`·`scikit-learn`·`joblib`·python) |
| 수치 열의 결측률이 적합 때와 유의하게 다름 | 그대로 실행 (대치는 학습 때 정한 그대로) | 폭 검사로는 절대 안 보이는 종류의 어긋남입니다. 문턱은 5%p **그리고** 그 배치 행 수에서의 2×표준오차 — 10행짜리 배치를 조용히 건너뛰지 않고 비교하되 잡음으로 줄을 만들지 않기 위해서입니다 |
| `-9999` 같은 결측 코드의 비율이 달라졌거나 새로 나타남 | 그대로 실행 ([센티넬은 감지하고 변환하지 않습니다](automl_agent/dataset/sentinels.py)) | 결측 코드의 비중이 움직이는 것은 결측률이 움직이는 것과 달리 평범한 일이 아니라 **규약이 바뀌었다는 신호**입니다. 그래서 문턱이 1%p로 훨씬 낮습니다. 적합 때 기록된 코드는 값을 그대로 세고(짧은 배치에 "규약이 바뀌었다"고 말하지 않기 위해), 기록에 없던 코드만 새로 감지합니다 |

### 경계는 그대로입니다

`feature_schema.json`은 범주 level과 클래스 라벨을 **그대로** 담습니다. 즉 셀 값입니다.
그래서 `model.joblib`·`val_predictions.npz`와 같은 편에 둡니다: `artifacts/` 안(gitignore),
경로가 `privacy.PUBLIC_RESULT_FIELDS`에 없고, 어떤 추론 노드도 읽지 않습니다
(`test_public_result_drops_both_halves_of_the_fitted_artifact`). 예측 결과 CSV도 행 단위
데이터이므로 같은 등급으로 다뤄야 하고, 명령이 끝날 때 그렇게 출력합니다.

`predict`가 노드가 아니라 명령인 이유도 이것입니다 — 모델을 고르는 일의 일부가 아니고,
**출력이 행 단위인 유일한 경로**라서 그래프 state에 아예 들어가지 않습니다.

### 라벨이 이미 있는 배치를 채점하기 — `--label-column`

정답 열이 있는 파일(백테스트, 지난달 마감된 배치)을 줄 때 그 열 이름을 `--label-column`으로
주면, **예측은 플래그 없을 때와 한 행도 다르지 않게** 그대로 나오고 거기에 점수가 붙습니다.
세 가지가 의도된 설계입니다.

**첫째, 이 점수는 이 실행의 채점 프로토콜이 아닙니다.** `result.json`의 홀드아웃은 어떤
모델도 적합되기 전에 떼어 둔 20%를 루프가 끝난 뒤 **한 번만** 채점한 값이고, 그 숫자의
의미는 그 절차에서 옵니다. 반면 이 파일이 어떤 행으로 이루어졌는지는 스크립트가 알 수
없습니다 — 다음 달일 수도, 다른 기관일 수도, 학습에 쓴 그 행들일 수도 있습니다. 그래서
점수를 낼 때마다 그 사실을 함께 출력합니다. "홀드아웃 0.71, 이 배치 0.62"는 누군가
**무엇과 무엇을 비교하는지 말하기 전까지는 서로 다른 두 가지에 대한 사실**입니다. 같은
이유로 신뢰구간에도 단서를 붙입니다: 이 행들이 한 대상에서 여러 번 나온 것이라면 행 단위
재표집 구간은 실제보다 좁습니다(새 파일의 군집 구조는 여기서 알 수 없습니다).

**둘째, 실행이 목표로 삼았던 지표로 채점합니다 — 그 지표가 있을 때.** 그 지표는 적합 때
`feature_schema.json`에 `metric`으로 기록되고, 채점은 홀드아웃을 채점한 것과 **같은
`evaluate_split()`** 을 지납니다. 채점하는 사람이 그때그때 고른 지표로 재면 두 숫자는
같은 측정이 아니게 됩니다. 레지스트리의 나머지 지표와 `specificity`, 그리고
`brier`·`calibration_error`([calibration.py](automl_agent/scoring/calibration.py))도 함께 나옵니다 —
후자는 50행 이상일 때만이고, 구간별 실제 발생률 표는 콘솔에만 찍습니다(구간마다 행 수가
들어가므로 프롬프트가 닿는 곳에는 두지 않습니다).

**그 지표가 이 task에 없으면, 거부가 아니라 대체합니다.** `RunConfig`는 지표 이름을 레지스트리와만 대조하고 task와는 대조하지 않습니다 — 프로파일링
**전에** 만들어져서 그때는 정답 열이 무엇인지 아무도 모릅니다. 그래서 분류 타깃에
`--metric rmse`가 플래그 검증을 통과하고, 카드가 `regression`이라 선언한 열이 실제로는
분류로 읽히면 `load_data`가 **열을 따릅니다**. 두 경우 모두 설정된 지표는 이 실행에 존재하지
않는 숫자가 되고, 그대로 두면 **모든 시도가 "목표 미달"로 기록되며 반복 예산이 다
소모됩니다** — 아무 시도도 잘못하지 않았는데.

예전에는 프로파일링 시점에 **거부**했습니다. 지금은 그 task의 기본 지표로 **바꿔서
실행합니다**([`metrics.substitute_metric`](automl_agent/scoring/metrics.py) — 분류 `f1`, 회귀 `r2`).
오타 하나가 긴 실행을 죽이는 것보다, 한 줄 경고와 함께 도는 편이 낫다는 판단입니다. 대체는
세 가지가 **함께** 움직여야 성립합니다:

- **방향을 새 지표에서 다시 읽습니다.** `rmse`의 `minimize`를 `f1`에 그대로 물려주면 실행
  전체가 뒤집힙니다 — `best`가 **가장 나쁜** 시도를 붙들고, 바 **아래**의 점수에서
  `goal_met`이 켜집니다. 고치려던 것보다 큰 결함입니다.
- **직접 준 `--threshold`는 버립니다.** 3.5는 정답 열의 단위로 준 오차이고, 그것을 `f1`의
  바로 재사용하면 아무 모델도 닿지 못하는 목표가 됩니다 — 대체가 막으려던 결과를 대체가
  만들어 냅니다. 버렸다는 사실과 다시 지정하는 방법을 함께 출력합니다.
- **한 곳에서만 바꿉니다.** 모든 노드가 `goal["metric"]`을 읽으므로
  [`goal.resolve_goal`](automl_agent/scoring/goal.py)이 유일한 진입점입니다. 아래쪽에서 각자
  대체하면 한 실행에 서로 다른 두 지표가 남습니다.

대체는 **조용할 수 없습니다.** 요청하지 않은 지표로 채점되는 실행이라서, 시작 시점의 경고와
`describe(goal)`의 괄호에 함께 남고 — 후자가 콘솔 헤더·Critic 프롬프트·`report.md`가 모두
읽는 그 한 줄입니다. `run_config.json`은 **입력한 값을 그대로** 유지합니다: 물어본 것과
채점된 것을 한 필드로 합치면 대체가 있었다는 증거가 사라집니다.

`train.py`도 같은 대체를 **한 번 더** 합니다([`goal_metric`](automl_agent/scripts/train.py)).
위쪽 대체는 **카드**의 task를 보고, 이 스크립트는 **열**을 보기 때문에, 카드가 열을 잘못
설명하면 플래그가 모두 일관된 실행 안에 같은 어긋남이 다시 들어옵니다. 그대로 두면 결과가
네 갈래로 흩어져 각각 다른 것처럼 보입니다 — 부트스트랩 구간이 "split too small"로 빠지고,
직전 최고와의 짝지은 비교가 `degenerate`로 빠지고, 과적합 gap이 아무도 고르지 않은 지표로
재지고, 스키마에는 배치가 절대 낼 수 없는 지표가 적힙니다. 그래서 네 개가 **한 숫자**를
씁니다.

그래도 `predict`에는 "이 배치에는 목표 지표가 없습니다" 줄이 남아 있습니다. 스키마에 적힌
지표를 **이 행들에서** 낼 수 없는 경우(한 클래스뿐인 배치의 `roc_auc`)와, 대체 이전에
만들어진 스키마 파일이 그것입니다. 헤드라인이 **유일한 신뢰구간**을 함께 들고 가기 때문에,
없어진 것을 없어졌다고 말하지 않으면 남은 목록이 "그중 하나가 목표인 점수표"로 읽힙니다.

**셋째, 라벨은 스키마의 `classes` 목록으로 코딩합니다 — 이 파일에서 다시 유도하지 않습니다.**
이것이 `predict.py` 전체가 막으려는 그 결함의 한 단계 위 판본입니다. `encode_target`은
눈앞의 열에서 범주를 뽑으므로, 한 클래스가 우연히 없는 배치에서는 남은 라벨이 `0..n-2`로
**다시 번호가 매겨집니다** — 모델이 `survived`라는 뜻으로 내놓은 `1`이 파일의 다른
클래스와 대조되고, 그 위의 모든 지표는 아무것에 대한 것도 아닌 숫자가 되며, **모델이 갑자기
망가진 것처럼 보입니다.** 스키마에 코드가 없는 라벨의 행은 채점에서 빼고 세는데, 빈 셀과
"학습 때 없던 값"은 **원인이 다른 문제라 따로 셉니다** — 새 클래스는 알려야 할 소식이고,
그것을 음성으로 취급해 계산한 점수는 그 소식을 묻어 버립니다.

무엇을 하지 않는지: 점수가 모델을 바꾸지 않습니다. 이 프로세스는 이 행들에 무언가를 적합할
권한이 없고(그래서 재캘리브레이션도 없습니다), 이 파일의 군집 구조를 모르므로 그룹 단위
재표집도 하지 않습니다. 채점 결과는 예측 CSV 옆의 `--report` JSON에 함께 들어가며, 행 단위
데이터와 같은 등급으로 다뤄야 합니다.

### 측정하지 않은 것

- 위의 19행/200행은 **이 한 쌍의 파일에서 측정한 값**입니다. 어긋남의 크기는 모델이 그
  level에 얼마나 기대고 있었는지에 달렸습니다. 같은 코드에서 10% 비중의 약한 level을
  바꿨을 때는 라벨이 하나도 뒤집히지 않고 평균 |Δp| 0.0014였습니다. **구조적으로 조용한
  것이 사실이고, 피해의 크기는 사례마다 다릅니다.**

## 두 번째 모드 — 연속 정답 열 (회귀)

같은 CLI, 같은 그래프, 같은 아티팩트 레이아웃입니다. 바뀌는 것은 **task 하나**이고,
그 task는 고르는 값이 아니라 정답 열에서 읽힙니다.

### task는 열이 정합니다 — `targets.detect_task`

라벨이 있는 행만 보고, 이 순서로:

1. 수치가 아닌 열(문자열·범주형)은 분류입니다. 다른 것일 수 없습니다.
2. 불리언은 분류입니다 — 수치 규칙이 0/1 int로 보기 **전에** 잡습니다.
3. 고유값이 2개면 dtype과 무관하게 분류입니다. `0.0`/`1.0` float로 저장된 라벨을
   단위구간 위의 회귀로 읽지 않으려는 것입니다.
4. float 열에 정수가 아닌 값이 하나라도 있으면 회귀입니다. `2.5`는 클래스 코드가 아니고,
   이것이 **고유값이 적은 연속 열**을 잡는 검사입니다(반올림된 3값 점수는 분류로 남습니다 —
   그 열이 다른 말을 하지 않으므로 정직한 결과입니다).
5. 나머지는 개수가 정합니다 — `CLASSIFICATION_MAX_DISTINCT = 20`.

고유값이 2개 미만인 열은 task가 아니라 **거부**입니다(`TargetUnusableError`): 상수 정답에는
배울 신호가 없고 모든 지표가 퇴화합니다. 실수로 한 결과만 남게 필터한 데이터가
"완벽한 점수"를 보고하는 대신 여기서 멈춥니다.

`encode_target`은 회귀에서 그 행들의 숫자를 **`float64` 그대로** 돌려줍니다 — 클래스 코드로
바꾸지 않습니다. 연속 열을 코드화하면 행마다 "클래스" 하나인 분류기를 학습시킵니다.

### 각 층이 어떻게 갈라지는가

| 층 | 분류 | 회귀 |
| --- | --- | --- |
| 지표 ([metrics.py](automl_agent/scoring/metrics.py)) | `f1` `accuracy` `balanced_accuracy` `precision` `recall` `roc_auc` `pr_auc` | `r2` `mae` `rmse` |
| 기준선 ([profile.py](automl_agent/scripts/profile.py)) | `LogisticRegression` | `Ridge` (median 대치 + 표준화) |
| chance | `DummyClassifier(strategy="prior")` | `DummyRegressor(strategy="mean")` |
| 분할 ([splits.py](automl_agent/scoring/splits.py)) | 층화 | **층화 안 함** — 나눌 층이 없습니다. `protocol.stratified: false`로 카드에 기록됩니다 |
| 카드의 정답 블록 | `class_balance` (정렬된 빈도) | `target` — 열 하나의 버킷들(`magnitude`, `skew`, `outlier_rate`). `mae` 바 3.5는 그 열이 단위인지 천 단위인지 모르면 읽을 수 없고, 카드에서 그것을 말해 주는 유일한 필드입니다 |
| 학습 지표 `train_*` | `f1`, `accuracy` | `r2`, `mae` |
| 진단 지표 | `specificity`, `balanced_accuracy_at_best_cut`, `cut_headroom`, `brier`, `calibration_error` | 없음 — 옮길 작동점도, 확률도 없습니다 |

지표는 **빠질 수 있고, 빠지는 쪽이 맞습니다.** `roc_auc`는 확률이 없는 모델에서, 그리고
`y_true`에 한 클래스만 있는 분할에서 낼 수 없습니다. 후자에서 sklearn은 예외를 던지지 않고
**NaN을 돌려줍니다** — 그 NaN을 그대로 담으면 세 방향으로 동시에 틀립니다: `json.dumps`가
`NaN`이라고 써서 `result.json`이 엄격한 JSON 파서에게 깨지고, NaN과의 모든 비교는 거짓이라
목표 검사가 "바에 못 미쳤다"로 읽고, 요약은 그것을 `roc_auc=nan`이라는 숫자처럼 찍습니다.
그래서 [score_split](automl_agent/scripts/train.py)이 유한하지 않은 값을 **이유와 함께 버립니다** —
키가 없는 것은 "재지 못했다"이고, NaN은 "쟀는데 이 값이다"라서, 없는 편이 정확합니다.

같은 판단이 파일 쓰기에도 한 번 더 걸립니다. `score_split`은 **한 생산자**를 막고,
`write_result`는 **모양**을 막습니다 — 다른 키로 들어온 NaN(짝지은 비교의 delta, 학습 분할
점수, 나중에 추가될 블록)은 그 앞을 지나지 않기 때문입니다. `result.json`을 쓸 때 유한하지
않은 값은 경로 이름과 함께 빼고(`nonfinite_dropped`, 로그 tail에도 같은 줄), 그다음
`allow_nan=False`로 직렬화합니다. 그 예외에 걸리는 것은 **이 함수의 버그**라는 뜻이고, 그때도
파일은 씁니다 — 숫자 몇 개가 빠진 유효한 파일이, 읽을 수 없는 파일보다 낫습니다(결과 파일이
없으면 오케스트레이터는 그 반복을 크래시로 기록해서, 학습이 한 일처럼 보이게 됩니다).
파이썬의 `json.loads`는 맨 `NaN`을 **받아들이기** 때문에 이것이 오래 눈에 띄지 않았습니다 —
`jq`나 다른 언어로 읽는 쪽에서만 깨집니다.

모델 레지스트리는 task별로 하나씩입니다([model_selection.py](automl_agent/nodes/model_selection.py)).
가족이 양쪽에 다 있으면 **id를 같게 두었습니다** — `hist_gbdt`는 양쪽에서 같은 단어라서
한쪽 카드에 대고 쓴 계획이 다른 쪽에서도 같게 읽히고, `capabilities`가 어휘 하나만
공개합니다. 다른 것만 적으면: 분류에만 `logreg`·`svc`, 회귀에만 `ridge`·`linreg`·
`elasticnet`·`svr`.

JSON 스키마의 enum은 **호출마다** 그 task의 레지스트리에서 만듭니다. 그래서 다른 task의
모델 이름은 제안될 수 없고, 그래도 온 이름은 orchestrator에서 `normalise_model`이
같은 가족의 가장 싼 모델로 고치고, 실행기에서 `build_estimator`가 거부합니다 —
`unsupported_model` 결과이지 예외가 아닙니다.

### `[0, 1]`을 전제했던 상수들

`mae`는 정답 열의 단위로 나옵니다. 0.15라는 간격은 확률에서는 거대하고 달러에서는
아무것도 아닙니다. 그래서 절대 거리였던 상수가 모두 **비율**이 되거나 **방향을 읽게**
되었습니다.

- `train_val_gap`은 언제나 **"검증이 학습보다 얼마나 나쁜가"**입니다. 오차 지표에서
  `train - val`은 과적합일 때 정확히 음수가 되므로, 방향을 [train.py](automl_agent/scripts/train.py)
  한 곳에서 적용하고 모든 소비자는 양수를 과적합으로 읽습니다.
- Critic의 과적합 판정은 유계 지표에서 `gap > 0.15`, 그렇지 않으면
  `gap > train_score × 0.25` — "검증이 학습보다 1/4 나쁘다"는 단위를 건너 옮겨지고
  0.15는 안 됩니다. 학습 점수가 없거나 0 이하면 **발동하지 않습니다**(안전한 쪽 —
  뒤의 분기가 여전히 진단합니다).
- 용량 부족 판정도 방향을 읽습니다: minimize에서는 `train_score > threshold × 1.05`,
  maximize에서는 `train_score < threshold - 0.05`.
- `data_issue` 처방이 갈립니다. 분류에서는 `class_weight="balanced"`가 처방의 전부이지만
  연속 열에는 그런 레버가 없어서, 회귀에서는 가족을 바꾸라고 말합니다
  (`{"model_family": "different"}`). 하이퍼파라미터가 아닌 것이 의도입니다 —
  `fallback_plan`은 `model_family`를 hyperparams에 병합하지 않고 따로 읽으므로,
  실행기가 버려야 할 키로 도착하는 것이 없습니다.
- Critic 프롬프트의 6·7·8번(작동점·`cut_headroom`·가중치 보간)은 이진 결정 규칙에 대한
  것이므로 이진 목표에서만 적용된다고 **정적 산문으로** 범위를 좁혔습니다. 프롬프트
  렌더러는 `{{var}}` 치환뿐이고 조건문이 없습니다.

## 종료 조건 — `route()`

세 조건 중 하나라도 만족하면 `report`로 갑니다. 그 외에는 `critic`을 거쳐
`planning`으로 되돌아갑니다.

1. 목표 지표 달성
2. `iteration >= max_iterations`
3. 정체: `stall_count >= 2` (개선 없는 반복이 연속 2회)

2번과 3번이 함께 무한 루프를 불가능하게 만듭니다. 목표를 못 채워도 `best`
스냅샷을 근거로 보고서는 반드시 작성됩니다.

## 실패 taxonomy

`underfitting` · `overfitting` · `data_issue` · `hyperparam` · `oom` ·
`too_slow` · `wrong_model_family` · `unknown`

`oom` / `too_slow`일 때 Critic의 `direction`은 **더 작은 모델, 반복·추정기 수 축소,
`train_subsample`** 를 가리킵니다 — 실행기에서 실제로 footprint를 줄이는 것은 이 셋뿐입니다.
`batch_size` 축소와 `precision: fp16`은 [guard_memory()](automl_agent/scripts/train.py)의
**추정치만** 낮춰 가드를 통과시키는 용도이고, 학습 자체를 가볍게 하지 않습니다.
스키마 파싱이 실패하면 **한 번 재시도한 뒤 `unknown`으로 폴백**합니다. taxonomy
밖의 `failure_type`은 `unknown`으로 강등되어 존재하지 않는 원인이 Planner
프롬프트를 오염시키지 않습니다.

### 환경이 실패할 때 — 쓰기 실패와 체크포인트 락

위 taxonomy는 **모델의 실패**를 분류합니다. 디스크가 차거나 다른 프로세스가 데이터베이스를
쥐고 있는 것은 그중 어느 것도 아니고, 제안을 바꿔서 나아지지도 않습니다. 그래서 이 셋은
따로 다룹니다.

- **iteration이 자기 config를 못 쓸 때** — `train_config.json` 쓰기가 실패하면 그 시도는
  `error_type: write_failed`로 기록되고 루프는 계속됩니다. 예전에는 이 `OSError`가 노드
  밖으로 나가 프로세스를 끝냈습니다 — 파일 하나에 대한 traceback 때문에 이미 끝난
  iteration 전부를 잃었다는 뜻입니다. 콘솔 메시지는 이것이 학습의 실패가 **아니라고**
  명시하고, `write_failed`는 [critic.py](automl_agent/nodes/critic.py)의 `ERROR_TYPE_MAP`에서
  `config_error`와 달리 `data_issue`가 아니라 `unknown`으로 갑니다 — 꽉 찬 디스크는 컬럼을
  고쳐서 닿는 곳이 아닙니다.
- **`train.log`를 못 쓸 때** — 그 시도의 점수는 그대로입니다. 콘솔 출력은 이미 메모리에
  있고 `log_tail`도 거기서 잘리므로, 잃는 것은 사람이 나중에 읽을 사본뿐입니다. 그래도
  알립니다: 조용히 없는 `train.log`는 돌지 않은 시도처럼 보입니다.
- **`run_config.json`** — 임시 파일에 쓴 뒤 `Path.replace`로 이름을 바꿉니다. `run` 말고
  모든 명령이 이 파일에서 설정을 복원하므로, 중간에 끊긴 쓰기는 **실행은 디스크에
  온전한데 아무 명령도 읽을 수 없는** 유일한 상태를 만듭니다. rename은 됐거나 안 됐거나
  둘 중 하나입니다. 그럼에도 깨진 파일을 만나면(옛 실행, 손으로 편집, 손상된 디스크)
  경로와 복구 방법이 담긴 한글 메시지가 나옵니다 — json 내부의 traceback이 아니라.
- **체크포인트 sqlite** — 데이터베이스 하나가 모든 `thread_id`를 담으므로 `show`가 살아
  있는 `run`과 같은 파일을 봅니다. busy timeout은 60초이고(stdlib 기본값 5초는 이미 한
  시간을 쓴 실행이 기다릴 만한 시간보다 짧습니다), WAL을 켜서 쓰기 중에도 읽기가
  진행됩니다. WAL은 파일의 속성이라 한 번 켜면 남고, 파일시스템이 못 하면(네트워크 공유)
  저널 모드를 건드리지 않고 그냥 엽니다 — 이것은 동시성 개선이지 요구사항이 아닙니다.
  그래도 락이 풀리지 않으면 `database is locked`가 LangGraph 내부에서 올라오는데, 그
  traceback에는 원인(다른 프로세스)이 적혀 있지 않으므로 CLI 최상단에서 잡아 한글로
  바꿉니다.

## `scripts/train.py` 계약

고정된 검증 코드이며, config로 모델과 하이퍼파라미터만 받습니다.

```bash
# 학습 모드 — train 60%에 적합하고 val 20%를 채점, model.joblib을 남깁니다
python -m automl_agent.scripts.train --config <path> --out <path>

# 채점 모드 — 아무것도 적합하지 않고, 저장된 모델을 test 20%에서 1회 채점합니다
python -m automl_agent.scripts.train --config <path> --out <path> --score-model <model.joblib>
```

`result.json`:

```json
{
  "metrics": {"f1": 0.83, "accuracy": 0.86, "balanced_accuracy": 0.71,
              "precision": 0.79, "recall": 0.88, "roc_auc": 0.90, "pr_auc": 0.62,
              "train_f1": 0.89, "train_val_gap": 0.06, "specificity": 0.64,
              "balanced_accuracy_at_best_cut": 0.79, "cut_headroom": 0.08,
              "brier": 0.1042, "calibration_error": 0.0371},
  "split": "val",
  "applied_hyperparams": {"max_iter": 200},
  "dropped_hyperparams": ["max_depth"],
  "applied_preprocessing": {"impute": "median", "scale": false,
                            "missing_indicator": false, "missing_count": false},
  "train_time_sec": 12.4,
  "status": "ok",
  "error_type": null,
  "log_tail": "...",
  "model_path": "...\\iter_01\\model.joblib",
  "schema_path": "...\\iter_01\\feature_schema.json"
}
```

- **`split`이 이 숫자가 어느 행에 대한 것인지 말합니다** — 학습 모드는 `"val"`,
  `--score-model`은 `"test"`. 같은 파일 하나가 두 모드를 다 하는 이유는 원본 행을 여는
  코드를 늘리지 않기 위해서이고, 두 모드의 채점이 `evaluate_split()` 하나를 지나는
  이유는 보고서가 나란히 놓는 두 숫자가 같은 코드에서 나와야 하기 때문입니다.
- **`model.joblib`은 `result.json` 옆에 남습니다.** 최고 시도를 나중에 재적합 없이 다시
  채점하기 위한 것입니다. `model_path`는 파일에만 있고 state로는 올라가지 않습니다 —
  적합된 추정기는 데이터와 등가입니다([원본 데이터 경계](#1-구조로-일차-방어)).
  저장 실패는 절대 치명적이지 않습니다: 점수는 이미 벌어 놓은 것이라 로그만 남기고
  넘어갑니다.
- **`feature_schema.json`은 그 모델을 만든 인코딩입니다** — 같은 디렉터리, 같은
  fail-open 규칙, 같은 데이터 등가 취급(`schema_path`도 state로 올라가지 않습니다).
  이 파일 없이는 `model.joblib`을 새 행에 적용할 방법이 없고, 다시 유도하면
  [조용히 어긋납니다](#학습한-모델을-새-데이터에-쓰기--predict). `--score-model`도 이 파일을
  읽습니다 — 스키마가 없는 옛 실행만 예전처럼 다시 유도하고, 로그에 그렇게 적습니다.
  합성 데이터 실행에는 인코딩 자체가 없으므로 이 파일도 없습니다.

- `metrics`에는 [레지스트리](automl_agent/scoring/metrics.py)의 지표가 **전부** 들어갑니다.
  확률을 못 내는 모델이나 다중분류에서만 `roc_auc`/`pr_auc`가 빠집니다(그 이유도
  레지스트리의 `needs_proba`/`binary_only`에 선언되어 있습니다).
- `train_<metric>`은 `f1`·`accuracy`에 더해 **목표 지표**를 냅니다. `train_val_gap`도
  목표 지표 기준으로 잽니다 — 과적합 판정이 실제로 최적화하는 숫자를 따라가야 하니까요.
- `specificity`는 이진 분류에서만 나오고, `train_val_gap`처럼 **진단용**입니다 —
  레지스트리에 없으므로 `--metric`으로 겨냥할 수 없습니다. 전부 음성으로 예측하는
  모델이 1.0을 받는 지표라 목표가 될 수 없지만, `balanced_accuracy =
  (recall + specificity) / 2`이므로 이 둘이 **가중치를 어느 쪽으로 움직여야 하는지**
  말해 주는 유일한 숫자입니다.
- `balanced_accuracy_at_best_cut`과 `cut_headroom`도 이진 분류 전용 **진단용**입니다.
  앞은 `(1 + KS)/2`, 즉 이 모델의 랭킹을 어떤 임계값으로 잘라도 넘지 못하는
  `balanced_accuracy`이고, 뒤는 실제로 받은 점수와의 거리 — **임계값을 골랐다면 얻었을
  정확한 양**입니다. 실행기는 항상 `predict()`를 부르므로 그 컷은 적용되지 않고, 따라서
  도달한 점수로 인용하면 거짓말이 됩니다. `cut_headroom`이 작으면 컷은 이미 최적에 가깝고
  남은 격차는 랭킹에 있다는 뜻입니다 — `class_weight`가 아니라 모델 family나 특성입니다.
- `brier`와 `calibration_error`([calibration.py](automl_agent/scoring/calibration.py))는 **확률이
  확률로서 쓸 만한지**를 재는 진단값입니다. 레지스트리의 지표는 전부 랭킹(`roc_auc`)이나
  고정 0.5 컷의 0/1 판정(`f1`)에 대한 것이고, **완벽하게 랭킹하면서 체계적으로 과신하는
  모델은 그중 아무것에도 걸리지 않습니다** — 그런데 이 하네스는 임계값을 고르지 않으므로
  호출자가 실제로 손에 쥐고 쓰는 것이 그 확률입니다. `brier`는 양성 확률의 평균제곱오차,
  `calibration_error`는 10구간에서 예측 확률과 실제 발생률의 개수 가중 거리이므로 0.04는
  "평균 4%p 어긋남"으로 읽습니다.
  - **50행 미만에서는 `calibration_error`를 내지 않습니다.** 10구간에 40행이면 한 구간이
    4행이고 그 실제 발생률은 0·0.25·0.5·0.75·1 중 하나밖에 될 수 없어서, 잘 맞는 모델도
    몇 %p 어긋난 것으로 측정됩니다. **없음은 이상 없음이 아니라 측정하지 않았다는
    뜻이고**, 출력에 그렇게 적습니다. `brier`는 표본 크기에 편향되지 않으므로 20행에서도
    나옵니다 — 두 숫자의 요건이 달라서 하나의 문턱을 공유할 수 없습니다.
  - **재캘리브레이션은 하지 않습니다.** `CalibratedClassifierCV`도, 컷 이동도 없습니다.
    확률을 다시 맞추는 것은 라벨 있는 행에 무언가를 적합하는 모델 변경이고, 여기서 라벨이
    있는 행은 홀드아웃(한 번만 채점하고 아무것도 통제하지 않음)과 호출자의 백테스트
    파일(이 프로세스가 적합할 권한이 없음)뿐입니다. **재기만 하고 밝히고, 모델은 그대로
    둡니다.**

- 메모리 초과는 잡아서 `status="error", error_type="oom"` + **exit 0**으로
  보고합니다.
- 시간 예산 초과는 오케스트레이터가 `subprocess` timeout으로 끊고 `too_slow`로
  기록합니다.
- 프로세스가 `result.json` 없이 죽으면(하드 크래시) 오케스트레이터가 `crash`로
  기록하고 Critic 경로로 계속 갑니다.
- **`log_tail`은 디스크에만 남습니다.** state로 올라가는 것은 `public_result()`를
  통과한 숫자 metric·status와, 실패 시 스크러빙된 예외 한 줄(`error_summary`)뿐입니다.
- LLM이 제안한 하이퍼파라미터는 **이름이 맞는 것만** 적용됩니다. 모르는 키는 로그를
  남기고 버리고, `UNSUPPORTED_BY_HARNESS`에 등록된 키(예: xgboost의
  `early_stopping_rounds`)는 생성자가 받아들여도 버립니다. `plan.preprocessing`도
  `training.py`의 화이트리스트(`impute`, `scale`, `missing_indicator`,
  `missing_count`)만 통과합니다 — 구현되지 않은
  변환을 보고서가 "적용했다"고 쓰는 것을 막습니다.
- **좁혀진 결과가 기록으로 돌아옵니다.** `applied_hyperparams`는 sklearn 파라미터
  이름으로 실제 적용된 집합이고, `dropped_hyperparams`는 버려진 이름들입니다.
  `state["hyperparams"]`는 어디까지나 *제안*이라, 이전에는 보고서가 실행되지 않은
  설정을 그 점수를 낸 설정이라고 적었습니다. 성공한 시도는 적용된 집합을, 실패한
  시도는 제안을 인용합니다 — OOM을 낸 `batch_size`는 Critic이 봐야 하는 값이니까요.
- `preprocessing`은 config가 적은 대로 **실제로 파이프라인이 됩니다.** 이전에는
  아티팩트에 기록만 되고 실행기가 무시했기 때문에, `impute: "mean"`이라고 쓰인
  실행이 median을 돌렸습니다. 키가 없으면 예전 기본값(median, scale-sensitive
  모델에서만 스케일링)을 그대로 씁니다.
- **`missing_indicator`와 `missing_count`가 결측을 특성으로 만듭니다.** 앞은 입력
  열마다 0/1 열 하나를 덧붙이고(전 열 아니면 전무 — `features="missing-only"`는
  학습·검증에서 폭이 달라집니다), 뒤는 "이 행에서 재지 않은 항목이 몇 개인가"
  한 열을 덧붙입니다. 둘 다 대치 **앞에** 붙으므로 대치가 흔적을 지우기 전의
  결측을 봅니다. `impute: none`으로 NaN을 트리에 그대로 넘기는 경로는 열별 결측만
  보고 행 전체의 결측 개수는 못 보므로, `missing_count`는 그 경로가 표현할 수 없는
  유일한 신호입니다. 뒤집으면 `missing_indicator`는 그 경로에서 **정확히 잉여**입니다
  (측정했습니다 — 기록은 개발 저장소의 `FINDINGS-mimic.md`).
- 두 변환기는 `train.py`가 아니라 [features.py](automl_agent/dataset/features.py)에 있습니다.
  `FunctionTransformer`는 함수를 `module.qualname`으로 pickle하는데 `train.py`는
  프로덕션에서 항상 `__main__`으로 실행되므로, 거기 두면 적합된 파이프라인이
  `__main__.append_missing_count`를 기록합니다 — 같은 `__main__`을 가진 프로세스에서만
  열리는 이름입니다. `--score-model`이 같은 스크립트를 다시 띄우기 때문에 그 결함은
  **잠복했습니다**: 증상이 `model.joblib`을 여는 *다른* 모든 프로세스에서만 났습니다.
  round-trip 테스트로는 못 잡습니다 — 테스트는 모듈을 import하므로 프로덕션과 다른
  이름이 기록되니까요. `__module__`을 직접 보는 테스트가 그래서 따로 있습니다.
- **`applied_preprocessing`은 config가 아니라 만들어진 파이프라인을 읽습니다.**
  요청이 그대로 통하지 않는 경우가 있기 때문입니다 — `impute: "none"`은
  `hist_gbdt`·`xgboost`가 아니면 median으로 내려가고, 모르는 전략도 기본값으로
  내려갑니다. `applied_hyperparams`와 같은 이유로 필요하고, 없는 동안 실제로
  같은 종류의 사고가 났습니다: `{"impute": "none", "scale": false}`로 돈 실행의
  보고서가 카드의 `preprocessing` 블록을 인용해 median 대치와 스케일링을
  적용했다고 적었습니다. 이제 history digest의 `preprocessing`이 이 값이고,
  보고서 프롬프트는 카드가 아니라 그것을 인용하라고 지시합니다.
- `target_missing.policy`가 정답이 빈 행을 어떻게 할지 정합니다(`reject` | `drop`).
  `cat.codes`가 NaN을 `-1`로 매핑하기 때문에, 빈 라벨 하나가 이진 문제를
  `n_classes=3`으로 만들고 평균 방식을 macro로 바꿔서 모든 점수를 목표와 비교할 수
  없게 만들었습니다.

### 실행기 능력 목록 — `capabilities.py`

추론과 실행을 분리한 구조는 **추론 쪽이 실행기의 모양을 알 때만** 성립하는데, 그렇지
않았습니다. 실제 LLM 실행마다 계획이 "결측 지시자 컬럼을 추가한다", "balanced accuracy를
최대화하는 확률 컷오프를 고른다"고 적었지만 당시 `scripts/train.py`는 둘 다 하지 않았습니다
(앞의 것은 그 뒤 실행기에 들어왔습니다 — [아래](#요구가-반복되면-능력이-된다)).
하이퍼파라미터 키로 오면 `dropped_hyperparams`에 남아 기록은 정직해지지만, **산문으로
오면 그대로 보고서의 `## 최고 성능 구성`까지 살아남습니다.**

한 실행은 기록이 아니라 점수로 값을 치렀습니다. iteration 2가 threshold sweep이 보정해 줄
것을 기대하며 `class_weight='balanced'`를 뺐고, 존재하지 않는 sweep 때문에
balanced_accuracy가 0.7863 → 0.6519로 떨어졌습니다.

[capabilities.py](automl_agent/capabilities.py)가 그 목록 하나를 소유합니다.
`run_training`/`build_estimator`를 읽어 쓴 것이고(의도가 아니라 코드가 출처),
`describe()`가 planning·critic·report 프롬프트에 같은 블록을 주입하므로 템플릿이 실행기와
어긋날 수 없습니다. 지금 목록에 없는 것: threshold 튜닝, 교차검증, 특성 공학
(`missing_indicator`·`missing_count` 두 열만 예외), 리샘플링(SMOTE 등), 확률 보정,
모델 결합(stacking/voting/seed averaging), 컬럼별 전처리, xgboost early stopping,
프로토콜 변경.

확률 보정은 여전히 목록 밖이지만, **그 어긋남은 이제 잽니다** — `brier`와
`calibration_error`가 이진 시도마다 나오고, CANNOT 항목의 "대신 무엇을 하라"가 그 두 값을
읽으라고 말합니다([calibration.py](automl_agent/scoring/calibration.py)). 못 고치는 것과 못 보는
것은 다르고, 지금까지는 둘 다였습니다.

`unsupported_claims`는 계획과 진단의 산문을 훑어 그중 무엇을 전제했는지 이름으로 남기고,
`plan`/`critic`/`history`에 실려 보고서까지 갑니다. **표시만 하고 반려하지 않습니다** —
반려도 같은 iteration을 쓰고, 탐지는 부분 문자열 매칭이라 false positive로 멀쩡한 계획을
버리는 편이 더 나쁩니다. 마커를 여러 단어로 좁게 잡은 이유도 같습니다(`threshold` 하나만
쓰면 "목표 threshold에 도달"에서 걸립니다).

#### 요구가 반복되면 능력이 된다

`missing_indicator`는 CANNOT에서 CAN으로 **넘어온** 유일한 항목입니다. 옮긴 근거는 의견이
아니라 실행 하나였습니다: 5회 반복에서 Critic이 세 번 family를 바꿨는데(`hist_gbdt` →
`logreg` → `xgboost`) `roc_auc`가 0.859~0.871에 갇혔고, `cut_headroom`이 0.0029까지
떨어져 임계값 레버가 다 소진되었다고 말했습니다. 남은 격차가 탐색이 아니라 **정보**에
있다는 뜻이고, 계획들이 반복해서 요구한 것이 바로 그 정보였습니다.

목록을 옮기는 작업의 위험은 목록과 실행기가 조용히 어긋나는 것입니다. 그래서 능력을 넣기
**전에** 결속 테스트를 먼저 커밋했습니다 — `preprocessing_block`이 실제로 통과시키는 키
집합과 CANNOT 항목의 문구가 서로 iff가 되게 잡는 테스트입니다. 능력을 추가하자 그 테스트가
정확히 4건 깨졌고, 깨진 것을 하나씩 의도적으로 갱신한 것이 목록 수정의 전부입니다. 마커
5개(`missing indicator`, `indicator column`, …)를 지운 것도 그 4건 중 하나입니다 —
이제 그 문장은 위반이 아니라 정당한 요청입니다.

뒷이야기는 개발 저장소의 `FINDINGS-mimic.md`에 있습니다. 능력을 열어 준 뒤 그 능력이 **얼마를 사는지** 재 봤고, 그 크기는 분할을 바꾸자 남지
않았습니다. 능력이 취소되는 것은 아닙니다 — 측정이 no를 yes로 바꾸는 방법이라는 것과, 그 yes가
iteration 하나를 쓸 값이 있다는 보장은 별개라는 뜻입니다.

#### 오탐이 기본값이었다 — 부정 문맥 억제

목록을 프롬프트에 넣은 것이 오탐을 **유발했습니다.** 목록을 읽은 Planner는 목록에 *대해*
씁니다. 3회 반복 실행 하나에서 플래그 3건이 모두 그런 문장이었습니다 — "shifts the
operating point **without** threshold tuning", "**No** eval_set / early_stopping_rounds /
callbacks are requested (**blocked** by the executor)", "the executor **cannot** add
missing indicators". 그리고 보고서가 그 격차를 "계획이 의도한 레버 중 실행되지 않은 것"으로
설명했습니다. 계획이 말한 것의 정반대입니다.

그래서 `_is_negated`가 **방향을 봅니다.** 앞쪽 같은 절에 부정 단서가 있으면 순응으로 보고
버립니다(`without` · `cannot` · `no` · `blocked` · `instead of` …). 뒤쪽은 일반 단서로 읽지
않습니다 — "a threshold sweep **instead of** class_weight"는 sweep을 *요구*하는 문장이니까요.
뒤쪽에서는 주어를 부정하는 서술어만 봅니다("indicator columns **are forbidden**"). 같은
계획이 어디선 부정하고 어디선 의존하면 **여전히 잡힙니다** — 매치 하나하나를 보고, 부정되지
않은 하나만 있으면 충분합니다.

같은 이유로 `cut-off`/`cutoff` 단일 마커는 버렸습니다. "recall 0.229 at the default 0.5
cut-off"는 실행기가 *하는 일*을 진단하는 문장이고 `class_weight`를 정당화하는 근거입니다.
고르는 행위를 마커가 함께 담아야 합니다(`optimal cutoff`, `pick the cut-off`, …).

실제 실행 6건으로 측정했습니다. 목록을 주입한 뒤의 두 실행(m-llm5·m-llm6)은 플래그 0건이
되고, 주입 전 네 실행은 진짜 의존(threshold 탐색·5-fold CV·결측 지시자·`eval_set`)을 그대로
유지합니다.

보고서 프롬프트는 이 이름을 **약한 증거**로 다룹니다: 원인으로 돌리기 전에 그 iteration의
`plan` 본문을 읽고, 계획이 한계를 *언급*만 했다면 손실로 쓰지 말고 `## 다음 단계 제안`으로
보내라고 지시합니다. `dropped_hyperparams`는 기계적으로 확인된 사실이라 그런 유보가 없습니다.
`## 최고 성능 구성`에는 어느 쪽도 들어가지 않습니다 — 실행된 것만 들어갑니다.

#### 그럼 없는 기능을 만들면 되는가

목록에서 가장 자주 요구된 것이 threshold 튜닝이고(`m-llm6` 보고서의 1순위 제안),
그래서 실제 데이터로 재 봤습니다: 최고 구성에서 홀드아웃 오라클 임계값조차 **+0.0024**
(0.7877 → 0.7901)이고, 기준선도 같은 프로토콜로 정직하게 재면 기준선이 +0.1490 좋아져
`auto` 바가 0.8038 → **0.8783로 올라갑니다.** 즉 만들면 이 실행은 더 크게 실패합니다.
값은 다른 데 있었습니다 — `class_weight`를 뺀 시도(roc_auc는 그대로, balanced_accuracy
0.6519)를 0.7901로 되돌리는 **견고성**입니다. 그 결정은
[capabilities.py](automl_agent/capabilities.py)의 `threshold_tuning` 항목에 `instead`와 함께
남아 있습니다 — 못 하는 일 목록에서 대신 무엇을 하라고 말하는 자리입니다.

#### 대신 만든 것 — 가중치 맵과 운영점 진단

측정이 가리킨 두 곳만 열었습니다. 둘 다 새 기능이 아니라 **이미 있는 레버의 접근 경로**입니다.

- **`class_weight`를 맵으로 받습니다.** `'balanced'`는 가중치 비를 클래스 빈도에 고정하는
  *한 점*이고 최적점이 아닙니다 — MIMIC 표본에서 `'balanced'`는 8.08인데 측정된 최고는
  10이었습니다(0.7849 → 0.7895). 맵은 산문으로는 내내 제안 가능했는데
  `sanitise_hyperparams`가 dict를 버려서 **한 번도 실행되지 않았고**,
  `dropped_hyperparams`에도 남지 않아 기록에서조차 보이지 않았습니다. 이제
  `{"0": 1, "1": 10}`이 config까지 가고, 실행기의 `weight_map()`이 JSON 왕복을 복구합니다
  (JSON에 정수 키가 없어서 `{"0": …}`로 도착하는데 sklearn은 그걸 거부합니다). 클래스를
  정확히 한 번씩 덮지 않는 맵은 `fit` 안에서 터뜨리는 대신 `dropped_hyperparams`로 갑니다 —
  그 예외는 메모리 가드를 지난 뒤에 나서 iteration 하나를 씁니다. 키는 **클래스 코드**이고,
  순서는 카드의 `class_balance` 순서입니다(`cat.codes`가 그렇게 매깁니다).
- **Critic이 운영점 붕괴를 진단합니다.** roc_auc는 유지됐는데 임계값 의존 지표만 크게
  떨어지면(m-llm4 it2: 0.7863 → 0.6519, roc_auc는 0.8704 → 0.8734로 *상승*) 순위는 그대로이고
  판정 규칙만 움직인 것입니다. 규칙 기반 폴백은 이것을 `underfitting`으로 읽고 용량을 더
  쓰라고 처방했는데, 그 방향으로는 임계값 의존 지표가 돌아오지 않습니다. 이제 `data_issue`로
  보고 불균형 레버를 되살리라고 적습니다. 과적합 판정이 먼저이고(train/val 격차는 용량에 대한
  증거라 운영점과 독립입니다), 목표 지표가 `roc_auc`/`pr_auc`면 레지스트리의 `needs_proba`로
  분기를 건너뜁니다 — 그때는 같은 숫자가 정반대 진단이니까요.
- **Critic이 가중치의 방향까지 읽습니다.** 위의 두 개를 붙여 놓고 실제 LLM으로 돌려 보니
  (m-llm7) 새 결함이 나왔습니다: 세 시도 모두 recall이 specificity보다 0.14~0.19 낮았는데도
  Critic은 train/val 격차를 근거로 **양성 가중치를 8에서 5로 내리라고** 처방했고, Planner가
  반박해서 겨우 진행됐습니다. 격차는 용량에 대한 증거라 방향을 말해 주지 않는데, 방향을
  말해 주는 숫자가 애초에 결과에 없었습니다. 이제 실행기가 이진 분류에서 `specificity`를
  같이 내고, 두 값의 차이가 0.08을 넘으면 규칙 기반 진단이 `hyperparam`으로 판정하면서
  낮은 쪽을 인용해 한 스텝(×1.5, 상한 1000)을 처방합니다 — 닫힌 해가 없으니 방향과 한
  스텝만 정하고 루프가 다시 측정합니다. 출발점은 `applied_hyperparams`의 가중치이고
  (`'balanced'`는 카드의 `class_balance` 비로 환산합니다), 프롬프트에도 같은 규칙이 규칙 6으로
  들어갔습니다. 과적합 판정이 여전히 먼저이고, `balanced_accuracy`처럼 두 쪽을 대칭으로
  평균하는 지표에만 적용합니다 — `f1`은 그 둘을 고르게 거래하지 않으니까요.
- **부호가 뒤집히면 스텝 대신 보간합니다.** 고친 뒤 다시 돌려 보니(m-llm8) 방향은 세 번 다
  맞았지만 스텝이 굼벵이였습니다. LLM Critic은 가중치 12에서 차이 +0.049, 8에서 −0.118을 보고
  "부호가 뒤집혔으니 사이"라며 10.5를 골랐고 그 점이 실제로 최적이었는데, 같은 자리에서 규칙
  기반 폴백은 8 × 1.5 = 12 — 너무 높다고 이미 측정된 점으로 되돌아갑니다. 이제 같은 모델의
  history에서 `(가중치, recall − specificity)` 짝을 모아 부호가 다른 두 점이 현재 값을 감싸면
  그 둘을 지나는 직선이 0을 만나는 곳을 처방합니다. 모델 family가 바뀐 점은 섞지 않고
  (m-llm8 iteration 4는 가중치를 그대로 두고 xgboost로 옮겼는데 차이가 −0.003 → −0.281로
  갔습니다), 단조성이 깨진 역전 쌍이나 지금 값으로 반올림되는 결과는 스텝으로 돌아갑니다.
- **어떤 컷으로도 넘을 수 없는 선을 미리 말해 줍니다.** m-llm7과 m-llm8은 같은 표본에서 바
  0.7842와 0.8038을 받았는데, 앞은 0.0005 차이로 통과하고 뒤는 네 시도 동안 0.7881을 넘지
  못했습니다. 탐색 품질 문제가 아닙니다 — 이진 목표에서 `balanced_accuracy`는
  `(1 + (TPR − FPR)) / 2`이고 `max(TPR − FPR)`이 KS의 정의이므로,
  **임계값에 대한 최댓값은 `(1 + KS)/2`라는 항등식**입니다. 이 표본에서 랭킹 둘을 재 봤는데,
  카드의 기준선 logreg는 KS 0.5168(상한 0.7584)이고 m-llm8의 최고 hist_gbdt는 KS
  0.5802(상한 0.7901 — 홀드아웃 오라클 임계값이 정확히 이 값을 냈습니다)입니다. 0.8038은
  **둘 다 넘습니다**. 그래서 (a) `profile`이
  카드의 `baseline`에 `ks`와 `balanced_accuracy_at_best_cut`을 싣고, (b) `auto`가 바를 그
  선과 비교해서 넘으면 통과 가능한 `passable_margin`(여기서는 0.384)과 함께 **공개**하고 —
  바는 낮추지 않습니다 — (c) 실행기가 매 이진 시도에 `cut_headroom`(상한 − 실제 점수, 여기서는
  +0.0024)을 붙입니다. 이건 이 데이터의 성질이 아니라 **이 모델 랭킹의 성질**이라, 넘었다는
  말은 "불가능하다"가 아니라 "랭킹 자체를 올려야 한다 — 특성이나 모델 family"입니다
  (m-llm8은 roc_auc를 0.8294에서 0.8738로, 상한을 0.7584에서 0.7901로 올렸습니다).
  그래서 카드의 상한은 **기준선의 한계일 뿐 실행의 한계가 아니고**, 경고는 보수적인 쪽으로
  틀립니다 — m-llm7의 바 0.7842에도 붙는데 그 실행은 0.7847로 통과했습니다. 그게 오탐이
  아닌 이유는 경고가 하는 말이 "불가능하다"가 아니라 "랭킹을 올려야 한다"이고, m-llm7이
  실제로 그렇게 통과했기 때문입니다. `cut_headroom`은 `specificity`와 같은
  진단값이고 목표로 삼을 수 없습니다 — 실행기는 항상 `predict()`를 부르니 그 컷은 적용되지
  않습니다. Critic 프롬프트는 운영점을 건드리기 *전에* 이 값을 읽고, 작으면
  `wrong_model_family`로 가라고 지시합니다. 실제 LLM으로 확인했습니다(m-llm9, 같은 표본·같은
  margin): 네 반복 전부 임계값 탐색을 요구하지 않고 `cut_headroom`을 근거로 인용하며, 세
  번째에서 `wrong_model_family`로 넘어갑니다. 네 랭킹의 상한이 0.7822~0.7933으로 전부 0.8038
  아래라 **어느 시도에서 완벽한 컷을 골랐어도 바에는 닿지 않습니다.** 설계하지 않은 용법도
  하나 나왔는데, 진단이 `balanced_accuracy_at_best_cut`을 계열 간 비교로 씁니다 — "xgboost의
  최선의 컷조차 hist_gbdt의 최선의 컷보다 낮다"(0.7822 < 0.7929).
- **그 경고에 크기를 붙였습니다.** "랭킹을 올려야 한다"는 방향이고 척도가 아니어서, **계열
  교체가 그럴듯한 답으로 읽힙니다.** mv-llm-4·5·6이 그 값을 치렀습니다 — 셋 다 iteration 1을
  운영점에 쓰고, 부족분의 96%가 랭킹에 있다는 것을 iteration 하나 뒤 **레저에서** 알았습니다.
  같은 항등식을 반대로 읽으면 바가 요구하는 KS가 나오므로(`2 × 바 − 1`),
  [`ranking.required_ks`](automl_agent/scoring/ranking.py)가 그것을 계산하고 `reference`에
  `required_ks`·`ks_shortfall`로 실립니다. MIMIC 표본에서 바 0.822는 KS 0.644를 요구하고
  기준선은 0.4945이므로 랭킹이 **0.1495만큼** 올라야 하는데, 계열 교체로 측정된 `roc_auc` 이동은
  0.0022~0.0077입니다 — 이 비교는 그 숫자 없이는 할 수 없고, `goal_note`는 iteration 1의
  Planner가 이미 받는 문장입니다. 바는 하나이고 요구는 둘이며, **둘 다 크기를 가집니다.**

`public_result`의 화이트리스트도 같이 열었습니다. 스칼라와 평평한 배열만 남기고 있어서 **실제로
적용된 가중치 맵이 기록에서 사라졌습니다** — 이 배관이 막으려던 결함의 정확한 반대 방향입니다.
한 단계 깊이의 평평한 맵까지 통과시키고 중첩 구조는 여전히 버립니다.

## `scripts/profile.py` 계약

```bash
python -m automl_agent.scripts.profile --data <csv> --target <column> --out <card.json> \
  [--name <name>] [--seed 42] [--no-baseline] [--on-missing-target {reject,drop}] \
  [--group-column <column>] [--caveat <text> ...]
```

성공 시 exit 0과 함께 카드를 쓰고, 사람이 읽을 요약을 stdout에 냅니다. 실패 시 exit 1과
stderr(로컬 전용 — 프롬프트로 가지 않습니다). `profiling` 노드가 이 스크립트를 그대로
자식 프로세스로 호출하고(`--seed`는 `run --seed`에서 넘깁니다), `profile`
서브커맨드도 같은 코드를 씁니다.

카드의 `baseline` 블록이 [목표 임계값](#목표-임계값) `auto` 모드의 근거입니다.
`--no-baseline`으로 끄면 카드에 그 블록이 없고, `auto`는 지표별 기본값으로
폴백합니다(`fixed`는 영향을 받지 않습니다).

```json
"baseline": {
  "model": "logreg (median impute + standard scale)",
  "n_rows_used": 47144,
  "protocol": {"train_fraction": 0.6, "val_fraction": 0.2, "test_fraction": 0.2,
               "stratified": true, "seed": 42},
  "scores": {"f1": 0.3422, "accuracy": 0.9031, "roc_auc": 0.8294, "pr_auc": 0.3382, "...": "..."},
  "chance": {"f1": 0.0,    "accuracy": 0.8899, "roc_auc": 0.5,    "pr_auc": 0.1101, "...": "..."},
  "ci": {"level": 0.95, "unit": "row", "resamples": 400,
         "scores": {"f1": {"low": "...", "high": "..."}, "...": "..."}},
  "ks": 0.5168,
  "balanced_accuracy_at_best_cut": 0.7584
}
```

`protocol`은 **이 점수가 어느 행에서 나왔는지**입니다. `run`이 이 블록을 자기 설정과
대조해서 어긋나면 거부하므로, 다른 시드로 만든 카드의 바를 이 실행의 점수와 비교하는
일이 생기지 않습니다([채점 프로토콜](#카드의-프로토콜이-실행과-어긋나면-거부합니다)).
위 `scores`는 이 필드가 생기기 전 프로토콜(75% train / 25% 홀드아웃)로 잰 기록이라
그대로 재현되지 않습니다 — 카드를 다시 생성하면 train 비율이 줄어든 만큼 달라집니다.

`ks`는 기준선 랭킹의 `max(TPR − FPR)`이고, `balanced_accuracy_at_best_cut`은 `(1 + ks)/2` —
**어떤 임계값으로도 이 랭킹의 `balanced_accuracy`가 넘지 못하는 값**입니다. "이 랭킹"이
중요합니다: 이건 기준선의 한계이고, 더 좋은 모델은 넘어갑니다(같은 표본에서 hist_gbdt가
0.7881). 둘 다 홀드아웃 전체에 대한 집계라서 점수와 같은 공개 정책 아래 있습니다. 이진 목표가
아니거나 확률을 낼 수 없는 경우엔 두 키가 그냥 없고, `auto`는 상한 없이 진행합니다.

`scores`와 `chance`는 레지스트리의 지표를 전부 담고, `average_precision`은 `pr_auc`와
같은 값으로 함께 실립니다(sklearn 이름으로 쓴 카드도 같은 바를 도출하도록).

`ci`도 **전부** 담습니다 — 카드는 `--metric`이 정해지기 전에 쓰이므로 여기서 하나만
고르면 절반은 틀린 것을 고릅니다. `unit`은 `--group-column`을 준 카드에서 `"group"`이
되고, 이 블록이 없는 카드(구간을 낼 수 없었던 작은 슬라이스, 이 필드보다 앞선 카드)는
그냥 통과합니다 — `auto`는 구간 없이 진행하고 대신 주의 문장을 붙이지 않습니다.
자세한 것은 [부트스트랩 신뢰구간](#다시-뽑으면-얼마나-흔들리는가--부트스트랩-신뢰구간).

`encoding` 블록은 위 점수가 **어느 행렬**에 대한 것인지 말합니다
([범주형 열](#범주형-열--featurespy)). 카드의 열 목록이 아니라 이 행렬이 추정기가 받는
것이라서, 12열 중 3열이 제외된 실행을 "12개 특성으로 0.71"이라고 읽지 않게 됩니다.

```json
"encoding": {"numeric": 9, "one_hot_columns": 2, "one_hot_levels": 11,
             "dropped_high_cardinality": ["note"], "dropped_unsupported_dtype": [],
             "max_cardinality": 50}
```

정답이 비어 있는 행은 기본적으로 **거부**합니다 — 몇 행인지, `--on-missing-target drop`을
주면 몇 행이 남는지 말하고 exit 1로 멈춥니다. `drop`을 주면 그 행을 빼고 카드를 만들고,
`target_missing: {"policy": "drop", "n_dropped": 1}`을 카드에 기록합니다. 요약 줄도 "위
수치는 남은 행 기준"이라고 말합니다. `run`이 이 블록을 읽기 때문에, 기준선을 잰
데이터와 학습이 점수를 내는 데이터가 어긋나지 않습니다.

학습 실패와 달리 **프로파일링 실패는 Critic에게 넘기지 않습니다.** 카드가 없는 것은
실험 결과가 아니라 설정 오류라서 진단할 것도, 세울 계획도 없습니다. 노드가
`ProfilingFailed`를 던지고 실행이 멈춥니다.

## `scripts/predict.py` 계약

원본 행을 여는 세 번째이자 마지막 파일입니다(`profile.py`, `train.py`가 나머지 둘).
그래프의 노드가 아니고 어떤 노드도 이것을 부르지 않습니다 — 출력이 행 단위라서
state에 올라갈 수 없습니다.

```bash
# 보통은 이쪽 — iteration을 스스로 찾고 두 아티팩트를 짝으로 넘깁니다
python -m automl_agent.main predict --thread-id <id> --data <csv> \
  [--out <csv>] [--iteration <n>] [--id-column <column>] [--label-column <column>] \
  [--report <json>] [--artifacts-root <dir>]

# 고정 스크립트 자체 — 두 경로를 직접 줘야 합니다
python -m automl_agent.scripts.predict --model <model.joblib> --schema <feature_schema.json> \
  --data <csv> --out <csv> [--id-column <column>] [--label-column <column>] [--report <json>]
```

`--iteration`을 주지 않으면 서브커맨드가 **이 실행이 선택한 최고 시도**를 찾습니다:
체크포인트를 먼저 보고, 없으면 `history.json`의 `best.iteration`을 봅니다. 둘 다 답을
주지 않으면 성공한 시도가 없었다는 뜻이라 그렇게 말하고 멈춥니다. 손으로 `train/iter_03`을
고르는 것이 위험한 이유는 **모든 iteration에 모델이 있고, 최악의 것도 똑같이 잘
로드된다**는 것입니다.

출력 CSV는 `--id-column`(주었다면), `prediction`, 그리고 분류라면 `proba_<라벨>`
열들입니다. 입력 열은 다시 쓰지 않습니다 — 호출자가 이미 가진 데이터를 한 부 더
복사하는 일이라서.

```
record_id,prediction,proba_died,proba_survived
r0000,survived,0.1834,0.8166
```

- **`prediction`은 학습 파일이 쓴 단어입니다** — `0`/`1`이 아니라 `died`/`survived`.
  스키마의 `classes`가 `encode_target`의 코드와 인덱스로 맞춰져 있습니다.
- **확률 열 이름도 라벨입니다.** 코드가 아니라 `model.classes_`를 기준으로 붙이므로,
  학습 split에 한 클래스가 없었더라도 라벨이 밀리지 않습니다.
- 회귀는 `prediction` 하나뿐이고 실수입니다. 확률 열은 만들지 않습니다 — 연속값에
  0~1 신뢰도를 지어내는 건 없는 것보다 나쁩니다.
- 정답 열이 남아 있는 파일(백테스트)을 주면 그 열은 **스키마가 적은 이름으로** 특성에서
  빼고 버립니다. `--label-column`으로 그 이름을 주면 거기에 채점이 붙습니다
  ([위](#라벨이-이미-있는-배치를-채점하기----label-column)) — 이름이 스키마의 정답 열과
  다르더라도(`outcome_actual`) 특성에서 빠지고, 학습 파일에 없던 열로 세지 않습니다.
- 거부는 exit 1과 stderr 한 줄이고, 무엇을 거부하고 무엇을 알리기만 하는지는
  [위 표](#무엇을-거부하고-무엇을-알리기만-하는가)에 있습니다.
- `--report`는 같은 요약을 JSON으로도 남깁니다(`rows`, `drift`, `warnings`, 두 아티팩트
  경로, `--label-column`을 줬다면 `score`). stdout으로는 어느 쪽이든 한글 요약이 나옵니다.
- **`--report` 쓰기가 실패해도 예측은 실패가 아닙니다.** CSV는 그 시점에 이미 저장되어
  있으므로, stderr에 `report not written`과 **CSV 경로**를 적고 요약은 그대로 출력하며
  exit 0으로 끝냅니다. 예전에는 traceback으로 끝났고, traceback을 본 사람이 내리는 결론은
  "예측이 실패했다"입니다 — 그러면 이미 나온 행을 다시 계산하거나 쓸 수 있는 파일을
  버립니다.

### `local/`

원본 CSV, 그 CSV에서 만든 카드, 합성 demo 데이터처럼 **저장소에 들어가면 안 되는
것은 모두 여기 둡니다.** [.gitignore](.gitignore)가 이 디렉터리를 통째로 막으므로
"이 파일은 커밋해도 되나"를 파일마다 따질 필요가 없어집니다 — 공개해도 되는지는
디렉터리 하나에 대한 질문이 됩니다. 문서의 `--out` 예시도 기본적으로 여기를
가리키고, `make_demo_data.py`의 기본 출력도 `local/demo.csv`입니다.

파일 종류별 규칙(`*.csv`, `*.parquet`, `*.feather`, `*.xlsx`)은 그대로 남겨 뒀습니다.
`local/` 밖에 실수로 떨어진 데이터 파일도 걸리도록 두 겹으로 둔 것입니다.

### 실제 데이터로 확인하기 — `probe_real_data.py` (개발 저장소)

테스트 스위트가 할 수 없는 검사가 하나 있습니다. 모든 테스트는 합성 프레임이나 작은
픽스처에서 돌고, 거기서 스키마 불일치는 **테스트가 일부러 만든** 상황입니다. 실제 데이터는
어떤 픽스처도 재현하지 못하는 경우를 가져옵니다: **열도 같고 행 수도 같은데 뜻이 다른 두
파일** — 한쪽은 결측을 빈칸으로, 다른 쪽은 `-9999`로 적은 같은 표본. 이것이 조용히 통과하던
바로 그 경우이고(sklearn은 폭이 맞는 행렬을 받습니다), 이 프로브의 C 단계가 잡는 것입니다.

이 스크립트는 배포본에 없습니다 — 개발 저장소의 `tools/probe_real_data.py`입니다. 아래를 남긴
이유는 그것이 무엇을 잡는지가 이 코드의 성질에 대한 설명이기 때문입니다.

```powershell
python tools/probe_real_data.py --data <원본.csv> --card <카드.json> `
    --sentinel-data <같은_표본_다른_인코딩.csv> --out <저장소_밖_폴더>
```

다섯 단계는 각각 코드가 자기에 대해 하는 주장 하나에 대응합니다 — A 적합하고 스키마가 무엇을
기록했는지, B 떼어 둔 뒤쪽을 **라벨과 함께** 채점, C 같은 표본의 다른 인코딩에 적용, D 손으로
바꾼 라이브러리 버전, E 옛 version 스키마(거부가 아니라 **못 하는 검사를 이름으로**).

행은 한 줄도 출력하지 않습니다 — 열 단위 비율, 점수, 드리프트 줄만 나옵니다. 반면 **저장하는
것**은 이야기가 다릅니다: 모델·스키마·행별 예측 CSV는 모두 원본과 동등한 데이터이므로,
`--out`이 저장소 안이고 `.gitignore`가 막지 않는 위치면 **거부합니다**.

실제 MIMIC 표본에서 이 프로브가 처음 돌 때 찾은 것: C 단계에서 `sentinel_shift` 11줄
(`gcs` 0.0% → 99.6%)과 `missing_rate_shift` 4줄이 나오면서 `f1`이 0.4719 → 0.3179,
`brier`가 0.0654 → 0.2225, 확률 구간별 오차가 0.0121 → 0.3086으로 벌어졌습니다. 같은 모델,
같은 열, 같은 행 수입니다. 덤으로, 표본이 **정렬돼 있다는 것**도 드러났습니다 — 뒤쪽 30%에서
`cr_diff` 결측이 39.8% → 100.0%라서 위치 기반 분할은 다른 모집단을 만듭니다(그래서 B 단계
점수는 홀드아웃 점수와 비교할 수 없고, 드리프트 블록이 그렇게 말합니다).

### 아티팩트 레이아웃

```
artifacts/
  checkpoints.sqlite               모든 스레드의 체크포인트
  <thread_id>/
    run_config.json                resume이 복원하는 실행 설정
    dataset_card.json              profiling 노드가 만든 카드 (private `data` 블록 포함)
    profile.log                    프로파일링 자식 프로세스의 출력 — 로컬 전용
    report.md                      최종 보고서 (한글)
    history.json                   시도 이력 + 종료 사유 + best + holdout
    holdout.json                   최종 test 채점 결과 — 실행당 1회 (holdout 노드)
    holdout.log                    채점 자식 프로세스의 출력 — 로컬 전용
    llm/NNN_<prompt>_iterN.json    프롬프트·응답·usage 전량 (호출 실패는 `.error.json`)
    llm/NNN_<prompt>_iterN.dryrun.md  --dry-run은 렌더된 프롬프트만
    train/iter_NN/
      train_config.json            학습 스크립트 입력
      result.json                  학습 스크립트 출력 (log_tail·model_path·schema_path 포함)
      model.joblib                 적합된 파이프라인 — 데이터 등가이므로 state로 올라가지 않음
                                   (기본적으로 최고 시도의 것만 남습니다 — 아래 참조)
      feature_schema.json          그 모델을 만든 인코딩 — level·클래스 라벨을 그대로 담으므로
                                   model.joblib과 같은 등급 (predict가 이 짝을 요구함)
      train.log                    학습 로그
    predict/                       predict 서브커맨드의 기본 출력 위치
      <입력파일이름>_predictions.csv  행 단위 예측 — 커밋 금지, 프롬프트 금지
```

`NNN`은 두 writer가 공유하는 하나의 카운터라서 `--force` 재실행이 dry-run과 실제 경로를
섞어도 번호가 되감기지 않습니다. label에는 **iteration이 들어갑니다** — 예전에는 실제
실행이 `planning_attempt1`만 남겨서 3회 반복의 001·004·007이 전부 같은 이름이었습니다
(`attempt`는 반복 카운터가 아니라 파싱 실패 시의 교정 재시도 카운터이고, 그래서 2회차부터만
붙습니다).

디스크의 `dataset_card.json`·`result.json`·`*.log`는 경로와 예외 원문을 담고,
`model.joblib`은 적합된 추정기 자체를, `feature_schema.json`은 범주 level과 클래스 라벨을
그대로 담습니다. 사람이 디버깅할 대상이므로 일부러
남기고, state와 프롬프트로는 넘기지 않습니다. `llm/` 아래 파일에는 이것들이 들어가지
않습니다. `artifacts/`는 통째로 [.gitignore](.gitignore)에 있습니다 — 모델 파일이
저장소에 들어가지 않는 이유가 그것뿐이면 약하니까, 파일 이름은 `config.py` 한 곳에서
나오고 경로는 `PUBLIC_RESULT_FIELDS` 밖에 있습니다.

### 실행이 끝나면 진 시도의 모델을 지웁니다 — `--keep-models`

**측정값이 이 동작의 근거입니다.** 이 저장소의 `artifacts/`는 1.9 GB이고 그중 1.79 GB가
`model.joblib` 56개입니다. 가장 큰 하나는 **486 MB** — 한 iteration의 제안이 깊은 forest
였을 뿐이고, 그 시도는 이기지도 못했습니다. 루프에는 이것을 막는 것이 없습니다.
`guard_memory`는 **입력 행렬**에 값을 매기는데, 그 크기는 추정기가 무엇을 하든 같습니다.
그래서 긴 실행의 실제 한계는 메모리가 아니라 디스크입니다.

`report` 노드가 마지막에 정리합니다. `holdout`이 이미 최고 시도를 채점했고 `predict`가
찾아가는 것도 그 하나이므로, 남는 것은 **쓸 수 있는 모델**이고 지워지는 것은 아무 명령도
`--iteration` 없이는 닿지 않는 시도들입니다.

- **`--keep-models best` (기본)** — 최고 시도의 `model.joblib`만 남깁니다
- **`--keep-models all`** — 예전 동작. `predict --iteration <다른 번호>`로 진 시도를 쓸
  거라면 이쪽입니다
- **성공한 시도가 없으면 아무것도 지우지 않습니다.** best가 없다는 것은 적합이 한 번도
  성공하지 않았다는 뜻이고, 그러면 "진 시도"라고 부를 근거가 없습니다 — 실패한 실행이 남긴
  파일은 그 실행의 증거 전부이고, 사람이 그것을 들여다볼 확률이 가장 높은 순간입니다

**설명할 수 없는 삭제는 아낀 디스크보다 나쁩니다.** 그래서 지운 iteration 번호와 회수한
바이트, 그리고 남기려면 무엇을 줬어야 하는지가 콘솔에 찍히고 `history.json`의 `models`
블록에 기록됩니다. 나중에 "iteration 2의 모델이 없다"가 사고가 아니라 기록된 결정으로
읽히는 것이 요점입니다 — `predict`의 오류 메시지도 그 블록을 가리킵니다.

`feature_schema.json`은 **지우지 않습니다.** 킬로바이트짜리이고, 그 시도가 컬럼을 어떻게
인코딩했는지에 대한 기록이며, 그 시도의 숫자는 여전히 `history.json`에 있습니다.

모델 파일 크기는 저장 직후 로그에 나옵니다. 100 MB를 넘으면 그 사실이 한 줄 덧붙고, 단위는
KB가 아니라 MB·GB입니다 — `509234 KB`는 아무도 읽지 않는 숫자였고, 그것이 1.9 GB가 보이지
않았던 이유입니다.

`--dry-run`에서도 프롬프트는 **실제로 렌더링해서** 저장합니다. 템플릿에 미치환
placeholder가 없다는 것과, iteration 2의 계획 프롬프트가 iteration 1의
`failure_type`·`direction`을 실제로 싣고 있다는 것을 토큰 한 개 없이 감사할 수
있습니다.

## 예시 데이터셋 카드

| 파일 | 목적 |
| --- | --- |
| [dataset_card.json](examples/dataset_card.json) | 기본 tabular 이진 분류 (손으로 쓴 카드, 합성 데이터) |
| [dataset_card_hard.json](examples/dataset_card_hard.json) | 목표 미달로 예산을 소진하는 어려운 카드 |
| [dataset_card_oom.json](examples/dataset_card_oom.json) | `constraints.memory_limit_mb: 6` — 실제 OOM 경로 |
| [dataset_card_crash.json](examples/dataset_card_crash.json) | `simulate.fail: "crash"` — 서브프로세스 하드 종료 |

네 장 모두 `path` 없이 카드의 선언된 형태만 담고 있어 실행기가 그 형태대로 데이터를
합성합니다 — 카드 한 장으로 루프 전체가 돌아갑니다. 대신 `baseline` 블록이 없으므로
`auto` 모드는 지표별 기본값으로 폴백합니다.

**데이터 파일은 저장소에 포함하지 않습니다.** 이 설계 자체가 원본 행을 로컬에 두는 것을
전제하고, 개발에 쓴 임상 데이터는 재배포가 허용되지 않습니다. 그런 것들은 git이 통째로
무시하는 [`local/`](#local) 한 곳에 모읍니다. 실제 행으로 도는 전체 공정(프로파일링 →
기준선 측정 → `auto` 도출)을 보려면 합성 데이터를 만들어 쓰세요.

```bash
# 합성 CSV 생성기는 개발 저장소에 있습니다 (examples/make_demo_data.py).
python -m automl_agent.main profile --data local/demo.csv --target died \
  --metric roc_auc --out local/my_card.json
```

그 생성기는 난이도를 일부러 맞춰 둡니다 — 선형
기준선 roc_auc 0.7256, 부스팅 0.85 부근이므로 `auto`의 0.7942는 넘고 고정 기본값 0.90은
못 넘습니다. 양성 12.5%라서 `accuracy`의 chance(0.8745)가 고정 기본값 0.85보다 높다는
것도 같이 보입니다. 명령 모음은 [RUNBOOK.md](RUNBOOK.md)에 있습니다.

## 검증된 시나리오

`--dry-run` 4종이 모두 서로 다른 분기로 정상 종료합니다.

| 시나리오 | 결과 |
| --- | --- |
| `success` | iteration 3에서 f1=0.86 → 목표 달성 |
| `fail` | iteration 5까지 소진, best f1=0.73 → 최대 반복 도달 |
| `oom` | iteration 1 OOM → Critic이 linear + `train_subsample`로 축소 → iteration 3 달성 |
| `stall` | 동일 점수 3회 → 정체 조기 종료 |

실제 실행(`--no-llm`)으로도 확인했습니다.

- OOM 카드: `hist_gbdt` OOM → `logreg` f1=0.8456으로 회복. 오케스트레이터 생존.
- Crash 카드: 서브프로세스가 `result.json` 없이 죽었으나 오케스트레이터는 살아서
  Critic이 `unknown`을 반환하고 정체 가드로 종료, 보고서까지 기록.
- 중단 후 동일 `thread_id`로 `resume` → iteration 2부터 이어서 완주.

### 합성 데이터로 재현하는 두 모드 (8,000행 × 12 feature, 양성 12.5%)

원본 CSV에서 `run --data`로 시작해 `profiling` 노드가 카드를 만드는 전체 공정을
확인했습니다. 아래 두 실행은 개발 저장소의 `make_demo_data.py`로
만든 데이터라 그대로 재현됩니다 (명령은 [RUNBOOK.md](RUNBOOK.md) 4·5번).

| 실행 | 결과 | 최종 test |
| --- | --- | --- |
| `--no-llm`, `auto`(→ 0.8083), 3회 | iter 1에서 roc_auc=0.8545 → **목표 달성으로 종료** | 0.8427 (`selection_gap` +0.0119) |
| `--no-llm`, `fixed` 0.90, 3회 | 3회 소진(0.8545 → 0.8648 → 0.8565), best 0.8648, 최대 반복으로 종료 | 0.8412 (`selection_gap` +0.0236) |

같은 데이터·같은 모델·같은 점수인데 모드에 따라 종료 사유가 "목표 달성"에서 "반복 예산
소진"으로 바뀝니다. 0.90은 이 데이터에서 도달 불가였고, `auto`가 낸 0.8083은 logreg의
0.7444를 남은 여유의 25%만큼 이긴 지점입니다. `fixed` 쪽에서는 루프가 실제로 도는 것도
보입니다 — Critic이 `hyperparam`으로 진단하고 계획이 따라 바뀝니다.
`auto`를 더 밀어붙이려면 `--margin 0.5`(→ 0.8722)로 요구를 올리면 됩니다.

오른쪽 열이 [채점 프로토콜](#채점-프로토콜--3분할과-반복-밖-1회-채점)이 붙은 이유입니다.
시도를 3개 놓고 최댓값을 고른 아래쪽 실행에서 격차가 두 배가 됩니다 — 검증 점수만 보고
있으면 그 폭은 보이지 않습니다.

### 임상 데이터 (47,144행 × 14 feature, 재원중 사망률 11%)

원래 검증은 MIMIC 파생 코호트에서 했고, 그 기록은 **재현되지 않습니다** — 데이터도 카드도
사용 협약상 저장소에 없습니다. 전체 기록은 개발 저장소의 `FINDINGS-mimic.md`에 있습니다.
거기서 읽을 것:

- **지표 선택이 종료 조건을 지배합니다.** 같은 데이터에서 `f1`로는 5회를 돌고도 못 넘은 바를
  `balanced_accuracy`로는 1회에 넘었습니다.
- **바를 올리면 도달 가능한 것이 아니라 성공/실패 판정만 바뀝니다.** margin 0.5는 반복 4회를
  더 쓰고 test를 0.0016 올렸습니다.
- **랭킹 상한에 막히면 컷도 모델도 답이 아닙니다.** `exceeds_ranking_ceiling`이 실제로 발동한
  실행에서 계열을 세 번 바꿔도 상한 0.772~0.781에 고정됐습니다.
- **원본의 `-9999` 센티넬을 결측으로 읽지 않으면 기준선이 망가집니다.** 클리핑이 잃은 것은
  랭킹이 아니라 운영점이었습니다 (`ks` −0.0013 대 `f1` −0.0795).
- **결측 자체가 라벨과 상관이 있고, median 대치가 그것을 버립니다.**
- 그리고 **측정되지 않은 것** — 1행이 환자인지 재실인지가 이 표본에서는 확인되지 않았습니다.

## 명세와 다른 점

의도적으로 다르게 구현한 부분입니다.

1. **프레임워크가 pytorch가 아니라 scikit-learn**입니다(+ 선택적 xgboost). 이
   환경에 torch가 없고, 대상 태스크가 tabular 분류라 sklearn이 적합합니다.
   `scripts/train.py`의 입출력 계약은 명세 그대로입니다.
2. **`oom`은 CUDA OOM이 아니라 명시적 메모리 예산 초과**로 재현합니다
   (`constraints.memory_limit_mb`). CPU tabular 환경에서 도달 가능한 대체 경로이며,
   `status="error", error_type="oom"`, exit 0 계약은 동일합니다.
3. **State에 `evaluation` 채널을 추가**했습니다. `evaluate`가 계산한 파생 수치
   (score / improved / goal_met)를 담아 CLI 한 줄 요약을 출력하고, 재개된 실행에서도
   다시 출력할 수 있게 합니다.
4. **CLI에 `--no-llm`과 `--force`를 추가**했습니다. 각각 자격 증명 없이 실제 학습을
   검증하기 위한 것과, `thread_id` 재사용으로 이력이 섞이는 것을 막기 위한 것입니다.
5. **`profiling` 노드와 `data_ref` 채널을 추가**했습니다. 명세는 데이터셋 카드를 입력으로
   받는 것까지였지만, 그러면 카드를 손으로 쓰는 사람이 어디까지 적어도 되는지가 규약으로만
   남습니다. 카드 생성을 그래프 안의 결정론적 진입 노드로 만들고 원본 경로를 별도 채널로
   빼면, "LLM은 원본 데이터를 보지 않는다"가 프롬프트 문구가 아니라 구조가 됩니다.
6. **목표 임계값에 모드를 두었습니다.** 명세의 `goal`은 고정 숫자 하나였지만, 그러면
   종료 조건이 모델 품질이 아니라 데이터셋 난이도를 재게 됩니다 (검증에 쓴 임상
   코호트에서 `roc_auc 0.90`은 도달 불가, `accuracy 0.85`는 다수 클래스 예측기가
   이미 넘음).
   기본값인 `auto`는 `profile.py`가 재는 고정 기준선에서 임계값을 도출하고,
   `--goal-mode fixed --threshold`는 명세 그대로 동작합니다 — 숫자가 데이터 밖에서
   오는 경우(배포 요구사항, 규제 하한)에는 고정값이 맞는 답이기 때문에 둘 중 하나를
   버리지 않고 모드로 나눴습니다. [목표 임계값](#목표-임계값) 참조.
7. **분할을 2개가 아니라 3개로 두고, `holdout` 노드를 추가했습니다.** 명세의 루프는
   검증 점수로 반복하고 그 `best`를 보고하는 것까지였는데, 그러면 보고하는 숫자가
   **선택에 쓴 숫자와 같은 숫자**가 됩니다 — 반복이 늘수록 위로 치우칩니다. test 20%를
   첫 적합 전에 떼어 두고 루프가 끝난 뒤 1회만 채점하도록 바꿨고, 그 차이를
   `selection_gap`으로 보고서에 싣습니다. 노드를 `route()` **다음**에 놓은 것이 요점이고,
   측정된 폭은 demo.csv 3회 반복에서 +0.0236이었습니다.
   [채점 프로토콜](#채점-프로토콜--3분할과-반복-밖-1회-채점) 참조.
8. **범주형 열을 버리지 않고 인코딩합니다.** 명세는 데이터 형태를 명시하지 않았고 초기
   구현은 수치 열만 썼습니다. 문자열 열을 통째로 버리는 것은 임상 표본에서는 무해했지만
   (14열 전부 수치) 일반적인 표에서는 신호의 대부분을 버리는 동작이라, 프로파일러와
   학습기가 함께 부르는 인코딩 모듈 하나로 옮겼습니다.
   [범주형 열](#범주형-열--featurespy) 참조.
